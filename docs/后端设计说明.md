## 一、技术栈

| 层次 | 选型 | 版本 | 选择理由 |
|---|---|---|---|
| 语言 | Java | **21** | LTS，支持 switch 箭头语法、文本块、record |
| 框架 | Spring Boot | **3.5.16** | 自动配置 + 内嵌 Tomcat；3.x 基于 Spring 6（jakarta 包名） |
| 持久层 | MyBatis（starter） | 3.0.5 / mybatis 3.5.19 | SQL 可控，能体现手写 SQL 能力 |
| 数据库 | MySQL | 8.4 | utf8mb4 / InnoDB（支持事务与行锁） |
| 密码加密 | BCrypt（spring-security-crypto） | 6.5.11 | 自带随机盐，比 MD5 安全 |
| Token | jjwt | 0.12.5 | 签发/验签 JWT |
| 构建 | Maven | 3.9 | — |

**为什么不用 Spring Security 全家桶**：`spring-boot-starter-security` 会自动给所有接口加认证，本项目要自己控制白名单和两套认证机制（JWT + 会话 token），所以只引 `spring-security-crypto`（纯密码工具）。

## 二、分层架构

```
                        ┌─────────────────────────────┐
   前端请求  ────────►   │  LoginInterceptor           │  验 JWT（仅 /api/customer/**）
                        └──────────────┬──────────────┘
                                       ▼
                        ┌─────────────────────────────┐
                        │  Controller 层              │  管 HTTP
                        │  · 收请求、参数绑定          │
                        │  · 不写业务判断              │
                        │  · 包 Result                 │
                        └──────────────┬──────────────┘
                                       ▼
                        ┌─────────────────────────────┐
                        │  Service 层                 │  管业务
                        │  · 业务规则校验              │
                        │  · 流程编排（调多个 Mapper）  │
                        │  · 事务边界 @Transactional   │
                        │  · 抛 BusinessException     │
                        └──────────────┬──────────────┘
                                       ▼
                        ┌─────────────────────────────┐
                        │  Mapper 层（只有接口）        │  管数据
                        │  ← MyBatis 动态代理          │
                        └──────────────┬──────────────┘
                                       ▼
                        ┌─────────────────────────────┐
                        │  resources/mapper/*.xml     │  真正的 SQL
                        └──────────────┬──────────────┘
                                       ▼
                                    MySQL
                                       │
                        ┌──────────────┴──────────────┐
                        │ 成功 → Entity → DTO → JSON   │
                        │ 失败 → BusinessException     │
                        │      → GlobalExceptionHandler│
                        │      → Result（统一格式）     │
                        └─────────────────────────────┘
```

**核心原则**：

| 原则 | 体现 |
|---|---|
| 每层只干一件事 | Controller 不碰 SQL，Service 不碰 HTTP，Mapper 不做判断 |
| Entity 不出网络 | 所有对外数据都用 DTO，挡掉密码哈希和内部 id |
| 统一出口 | 所有响应（含错误）都是 `Result{code,message,data,timestamp}` |
| 全局异常 | Controller 里一行 try-catch 都没有 |

## 四、一次请求的完整链路（以"取款 500"为例）

```
ATM 机  POST /api/atm/withdraw
        body: {"sessionToken":"abc","amount":500}
   │
   ▼
① Tomcat 收到请求
   │
   ▼
② LoginInterceptor.preHandle()
     路径 /api/atm/** 在 WebMvcConfig 的白名单里 → 直接 return true（不验 JWT）
   │
   ▼
③ DispatcherServlet 路由到 AtmController.withdraw()
     · @RequestBody 把 JSON 反序列化成 WithdrawRequest 对象
     · @Valid 触发 Bean Validation：
          @NotBlank  会话令牌不能为空
          @NotNull   取款金额不能为空
          @DecimalMin(100) / @DecimalMax(5000)
       校验不通过 → 抛 MethodArgumentNotValidException → 跳到 ⑩
   │
   ▼
④ AtmServiceImpl.withdraw(request)     ← ★ 加 @Transactional，事务在此开启
     ├─ getValidSession(token)          校验会话：存在 / status=1 / 未超时5分钟
     │     └─ 调 atmSessionMapper.selectByToken()
     ├─ bankCardMapper.selectByCardNo() 查卡
     ├─ checkCardStatus(card)           校验卡状态（1正常/2锁定/3挂失/4注销）
     ├─ validateAmount(amount)          100 的整数倍 + 100~5000
     ├─ accountMapper.selectByCardId()  查账户
     ├─ accountMapper.decreaseBalance() ★ 扣款（WHERE 带余额校验，返回 0 行 = 余额不足）
     ├─ cashBoxMapper.selectByDeviceAndDenomination() 查钞箱
     ├─ cashBoxMapper.decreaseNoteCount() ★ 扣钞（WHERE 带张数校验）
     ├─ transRecordMapper.insert()       ★ 记流水 WITHDRAW
     └─ atmSessionMapper.updateLastActive() 刷新会话
   │
   ▼
⑤ Mapper 接口（没有实现类）
     MyBatis 动态代理拦截 → 用「namespace + 方法名」找到 XML 里的 SQL
   │
   ▼
⑥ 执行 SQL（MyBatis 把 #{} 编译成 ? 预编译参数）
   │
   ▼
⑦ 结果集映射成 Entity（列名自动下划线转驼峰：before_balance → beforeBalance）
   │
   ▼
⑧ ★ 事务 COMMIT（Service 方法正常返回时，AOP 代理提交）
     5 条 SQL 的修改一起落库
     （如果中途抛异常 → ROLLBACK，全部撤销）
   │
   ▼
⑨ 返回 AtmController → Result.success("取款成功", response)
   │
   ▼
⑩ Jackson（HttpMessageConverter）把 Result 序列化成 JSON 字符串
   │
   ▼
⑪ HTTP 200 + Content-Type: application/json + JSON body
   │
   ▼
⑫ LoginInterceptor.afterCompletion()
     UserContext.clear()  清 ThreadLocal（无论成功失败都会执行）
     连接归还 HikariCP 连接池
   │
   ▼
ATM 机收到 JSON，界面显示"请取走现金，余额 9500.00"
```

**异常分支**（④ 或 ③ 抛异常时）：

```
BusinessException / 校验异常
   → AOP 代理捕获 → 事务 ROLLBACK
   → 异常继续向上抛
   → GlobalExceptionHandler 对应方法接住
   → 包装成 Result{code, message, data:null}
   → Jackson 序列化 → 返回
```

## 五、八个关键设计决策（答辩重点）

### 5.1 为什么分三层，不让 Controller 直接调 Mapper

| 问题 | 后果 |
|---|---|
| 无法复用 | 以后加"手机银行取款"，60 行业务逻辑要抄一遍 |
| 事务范围错乱 | 事务会包住 JSON 解析和序列化，数据库连接占用更久 |
| 无法单测 | 测"余额不足"要启动整个 Web 容器 |
| 职责混乱 | 改需求不知道该改哪个文件 |

### 5.2 为什么 Service 返回业务对象而不是 Result

`Result` 是 Web 层的东西。Service 不该知道"HTTP 响应"这个概念。

- 定时任务调用 Service 时，拿到 Result 还得拆
- 单元测试要构造 Result 对象

**正确分工**：Service 返回对象/抛异常 → Controller 包 Result → 全局处理器包异常。

### 5.3 `@Transactional` 到底该不该加

**判断标准：需不需要"一起回滚"。**

| 方法 | 加不加 | 原因 |
|---|---|---|
| `withdraw` / `deposit` / `transfer` | ✅ **必须** | 动 2~3 张表，任何一步失败要全部撤销 |
| `verifyPassword` | ❌ **绝不能** | 抛业务异常会把"错误次数+1""锁卡""标记超时"一起回滚 → 用户能无限试密码 |
| `insertCard` | ⭕ 可加可不加 | 只有一条 insert，天然原子 |
| `queryBalance` / `queryTransactions` | ❌ 不用 | 只读，没有数据要回滚 |

> **规则**：要回滚才加；加了还要抛业务异常，必须配 `noRollbackFor = BusinessException.class`。

### 5.4 并发安全：三道防线（没有用 Redis 和分布式锁）

| # | 手段 | 代码位置 | 防什么 |
|---|---|---|---|
| 1 | **条件更新** `where available_balance >= #{amount}` | `AccountMapper.decreaseBalance` | 并发取款不会扣成负数（靠 MySQL 行锁） |
| 2 | **原子自增** `set pwd_error_count = pwd_error_count + 1` | `BankCardMapper.increasePwdErrorCount` | 计数不丢失（不能用"读出来加一再写"） |
| 3 | **唯一索引** `uk_trans_no` | `trans_record` 表 | 重复提交被数据库挡住（幂等） |

**为什么不用乐观锁 `version`**：`account` 表有 `version` 字段但没用。因为乐观锁只在"读出来→改→写回"的模式下才需要；本项目直接写 `set x = x - n` 让数据库原子更新，Java 侧没有 read-modify-write，不存在丢失更新。

**为什么不用 Redis / 消息队列**：
- JWT 无状态，服务器不存 Session
- 单机部署，MySQL 行锁足够
- ATM 是同步交易，没有异步削峰需求
- **引入中间件只增加复杂度，没有收益**

### 5.5 两套认证机制

| | 管理端 | ATM 端 |
|---|---|---|
| 令牌 | JWT | 数据库会话 token（32 位 UUID） |
| 存放 | 请求头 `Authorization: Bearer` | 请求体 `sessionToken` |
| 服务端存储 | 不存（无状态） | 存 `atm_session` 表 |
| 能否主动失效 | ❌ 只能等 2 小时过期 | ✅ 改 `status` 立刻失效 |
| 为什么这么选 | 管理员是内部人员，短有效期内无需踢人 | **ATM 是高安全场景**：退卡/挂失/超时必须立即生效，JWT 做不到 |

**拦截器白名单**里放行 `/api/atm/**`，**放行不等于不设防** —— ATM 接口在 Service 层用 `getValidSession()` 自己校验会话。

### 5.6 Entity 和 DTO 分离

| 场景 | Entity | DTO |
|---|---|---|
| `TransRecord` 19 个字段 | 全部（含 accountId、sessionId、deviceNo） | `TransDetailItem` 只暴露 9 个 |
| `SysUser` 有 password | 有（登录校验要用） | `LoginResponse` **没有** |

**两个作用**：① 防敏感信息泄露；② 接口形状可以和表结构独立演进。

### 5.7 手续费的三档设计

```java
BigDecimal fee = amount.multiply(new BigDecimal("0.005"))
        .setScale(2, RoundingMode.HALF_UP);   // 四舍五入到分
if (fee < 1)  fee = 1.00;                      // 最低 1 元
if (fee > 50) fee = 50.00;                     // 最高 50 元
```

**必须用 `BigDecimal` + `setScale` + `RoundingMode`**，不能用 `double`（浮点误差会让 1000 × 0.005 算出 4.999999999）。

**⚠️ BigDecimal 比较大小必须用 `compareTo()`，不能用 `==` 或 `equals()`**（`equals` 会比较 scale，`1000` 和 `1000.00` 不相等）。

### 5.8 转账的防死锁设计

```java
if (fromAccount.getId() < toAccount.getId()) {
    先扣本方，再加入对方
} else {
    先加入对方，再扣本方
}
```

**两个转账方向并发时，都能按相同顺序获取行锁，不会互相等待。**

## 六、两个状态机

### 6.1 银行卡状态（`bank_card.card_status`）

```
        ┌──────────────┐
        │ 1 正常        │
        └──┬────────┬──┘
           │        │
   密码错3次│        │挂失
           ▼        ▼
     ┌─────────┐  ┌─────────┐
     │ 2 锁定  │  │ 3 挂失  │
     └────┬────┘  └────┬────┘
          │            │
     柜台解锁│        │注销
          │            ▼
          │       ┌─────────┐
          └──────►│ 4 注销  │
                  └─────────┘
```

| 状态 | 能否插卡 | 触发方式 |
|---|---|---|
| 1 正常 | ✅ | 初始状态 |
| 2 锁定 | ❌ 2005 | 交易密码连续错 3 次（自动） |
| 3 挂失 | ❌ 2006 | 柜台办理 |
| 4 注销 | ❌ 2006 | 柜台办理 |

### 6.2 ATM 会话状态（`atm_session.status`）

```
        插卡
         │
         ▼
   ┌──────────┐  退卡   ┌──────────┐
   │ 1 进行中 │───────►│ 2 已退卡 │
   └────┬─────┘         └──────────┘
        │ 5 分钟无操作
        ▼
   ┌──────────┐
   │ 3 超时   │
   └──────────┘
        （4 异常：预留给系统故障）
```

**每次成功调接口都会刷新 `last_active_time`**，所以"连续操作"不会超时，只要中间停 5 分钟以上就会失效。

## 八、我是怎么验证的（四层）

| 层 | 做什么 | 抓什么错 | 成本 |
|---|---|---|---|
| **1. 静态结构检查** | 文件名↔类名、接口↔实现、XML namespace↔Mapper、XML id↔方法名、`@Param`↔`#{}`、实体字段↔数据库列、未用 import、`@Value`↔配置项、ResultCode 引用、Controller 路径重复、BOM、死代码 | 命名错、绑定错、字段漏 | 秒级 |
| **2. 真编译** | `javac` 手工拼 classpath 全量编译 50 个源文件 | 类型不匹配、找不到符号、未实现抽象方法 | 10 秒 |
| **3. 数据库校验** | 把 XML 里的列清单拿去 `select ... limit 0`；用 `explain` 验证所有 update/insert 语法 | 列名拼错（如 `expire_data`）、SQL 语法错（如少逗号、少空格） | 1 秒 |
| **4. 真请求 + 故障注入** | 发真实 HTTP 请求 → 查数据库比对期望值；故意造异常（钞箱改成 2 张、余额改成 300） | 运行时绑定错、业务逻辑错、事务没回滚 | 1 分钟 |

**为什么四层都要做**：编译通过 ≠ 正确。

本项目实际抓到的问题分布：

| 问题 | 被哪一层抓到 |
|---|---|
| `expire_data`（列名拼错） | 第 3 层 |
| UPDATE 少逗号 / `select<include/>` 少空格 | 第 3 层 |
| XML id `increaseNotCount` 拼错 | 第 1 层 |
| `@Param("device")` 应为 `"deviceNo"` | **只有第 4 层** |
| `@PostMapping("/transations")` 拼错 | **只有第 4 层** |
| `return null` 忘了返回对象 | 第 4 层 |

**结论：前三层负责快速筛掉低成本错误，第 4 层才是真正的防线。**

## 十、答辩可讲的技术亮点（10 条）

1. **分层架构 + 统一响应 + 全局异常** —— Controller 零 try-catch
2. **两套认证机制**：管理端 JWT（无状态），ATM 端数据库会话（可主动失效）—— 各自适配安全需求
3. **BCrypt 而非 MD5**：自带随机盐，同样的密码每次哈希不同
4. **登录失败统一提示**，防用户枚举攻击
5. **交易密码连续 3 次锁卡**，且用原子自增保证并发下计数不丢
6. **扣款的余额校验写在 SQL 的 WHERE 里**，靠数据库行锁保证不超扣
