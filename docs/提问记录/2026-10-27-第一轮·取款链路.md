## 第 1 题 —— `setState`

**问**：前端点了按钮之后，为什么必须调 `setState` 界面才会变？

**你的答案**：不知道

**评分**：❌

**正确答案**

Flutter 的界面是"算"出来的：

```dart
Widget build(BuildContext context) { ... }   // 这个方法负责把数据画成界面
```

`build()` **不会一直跑**，只在三种情况下被调用：

```
① setState(() { ... }) 被调用    ← 唯一的主动方式
② 父组件重画
③ 系统事件（窗口大小变化等）
```

所以改了普通变量却不调 `setState`，`build()` 不会执行 → **屏幕还是旧内容**。

**本质**：`UI = f(state)`。界面不是"被修改"的，而是"被重新生成"的。

**例外**：改 `TextEditingController` 不需要 `setState`，因为它内部是 `ChangeNotifier`，赋值时自己会通知界面。

**一句话记**：变量 = 草稿，`build()` = 打印机，`setState` = 按打印按钮。

## 第 2 题 —— ATM 接口为什么不校验 JWT

**问**：`/api/atm/withdraw` 这个接口为什么不校验 JWT？

**你的答案**：ATM 的请求不经过这个拦截器，它是用 `sessionToken` 在 Service 里面校验的

**评分**：✅ **完全正确**

**补充完整表述**

```java
// config/WebMvcConfig.java
registry.addInterceptor(loginInterceptor)
        .addPathPatterns("/api/**")
        .excludePathPatterns("/api/admin/login", "/api/atm/**", "/api/hello", "/error");
//                                        ↑ ATM 接口被排除，拦截器根本不执行
```

ATM 端改用 `getValidSession()` / `getVerifiedSession()` 在 Service 层校验会话状态和密码验证标志。

**为什么这么设计**：管理端是内部人员，JWT 无状态、短有效期就够；ATM 端要求"退卡/挂失/超时立即失效"，JWT 做不到，必须存在数据库里。

## 第 3 题 —— Controller 为什么没有 try-catch

**问**：Controller 里为什么一行 try-catch 都没有？

**你的答案**：它这里有全局异常处理

**评分**：⚠️ 方向对，但没说清"为什么这样就可以"

**正确答案**

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)               // 业务异常
    @ExceptionHandler(MethodArgumentNotValidException.class) // 参数校验失败
    @ExceptionHandler(Exception.class)                       // 兜底
}
```

**任何 Controller 抛出的异常都会被这里接住**，自动转成统一的 `Result` 格式。

**三个好处**：

```
① 14 个接口省掉 14 段重复的 try-catch
② 所有错误格式统一（都是 {code, message, data}）
③ 改错误提示只改一个地方
```

**这叫"横切关注点集中处理"** —— 错误处理不属于某一条业务流程，属于全局关切。

## 第 4 题 —— `@Transactional` 防什么 ⭐ 重点订正

**问**：取款方法上加 `@Transactional` 是干什么的？不加会怎样？

**你的答案**：`@Transactional` 是用来触发事务回滚的。不加的话，比如你先取 500 元，但你账户没有这么多钱，如果没有事务回滚，你就把 500 元取出来了，这样银行的账就对不上。

**评分**：⚠️ **概念对，例子举错了**

**问题在哪**

"余额不足却取出钱" 这个场景 **`@Transactional` 管不到**，它在第 5 步就被拦住了：

```java
int rows = accountMapper.decreaseBalance(account.getId(), amount);
if (rows == 0) throw new BusinessException(BALANCE_NOT_ENOUGH);   // 直接抛，压根没扣成
```

钱不够时是"根本没扣"，不是"扣了要退回"。

**两个不同的问题，不能混**

| 问题 | 谁来管 | 关键代码 |
|---|---|---|
| 钱不够，却扣成了负数 | **SQL 的 WHERE** | `where available_balance >= #{amount}` |
| 钱扣了，但没出钞 | **`@Transactional`** | 配钞失败 → 回滚 → 扣的钱退回 |

**`@Transactional` 真正防的是第二种**

```
第 5 步 扣钱 ✅ 成功（余额 9800 → 9300）
第 6 步 配钞 ❌ 钞箱只有 2 张（不够 5 张）→ 抛异常
        ↓
没有事务 → 钱扣了、钞没出 → 银行白赚 500，客户投诉
有事务   → 第 5 步的 UPDATE 被 ROLLBACK，余额还是 9800 ✅
```

**精确表述（背下来）**

> `@Transactional` 把方法里的多条 SQL 绑成一个事务，要么全部提交、要么全部回滚。
> 它防的是"多张表只改了一部分"的**数据不一致**，不是"余额够不够"的**业务判断**。

## 第 5 题 —— 余额判断为什么写进 WHERE ⭐ 核心

**问**：扣款为什么把"余额够不够"写在 SQL 的 WHERE 里，而不是先查余额再判断？

**你的答案**：不知道

**评分**：❌

**正确答案**

**朴素做法的漏洞：**

```java
Account acc = accountMapper.selectById(id);          // ① 读
if (acc.getAvailableBalance() >= amount) {            // ② 判断
    accountMapper.decreaseBalance(id, amount);        // ③ 改
}
```

```
余额 600，两个请求各取 500：

T1  请求A 读到 600
T2  请求B 读到 600        ← A 还没改，B 也读到 600
T3  请求A 判断 600 >= 500 ✅
T4  请求B 判断 600 >= 500 ✅
T5  请求A 执行 → 600-500 = 100
T6  请求B 执行 → 100-500 = -400     💥 负数
```

**根源**：①读 和 ③改 之间有时间窗口，别人的请求能插进来。
**你读到的余额，在写的时候已经过时了。** 这叫**竞态条件**。

**正确做法：把条件塞进 WHERE**

```sql
update account
set available_balance = available_balance - 500
where id = 1
  and available_balance >= 500          ← 判断和修改在同一条语句里
```

```
T1  请求A：600-500=100，影响 1 行 ✅
T2  请求B：WHERE 100 >= 500 不成立，影响 0 行
    → Java 收到 rows == 0 → 抛"余额不足" ✅
```

**为什么安全**：数据库执行 UPDATE 时给这一行**加行锁**，"判断 + 修改"是**不可分割的动作**。B 必须等 A 提交完才能执行。

**这个模式叫 CAS（Compare And Swap）/ 条件更新 / 乐观条件更新。**

## 第 6 题 —— 配钞失败怎么退回已扣的钱

**问**：第 6 步（配钞）失败时，第 5 步扣的钱怎么退回来的？

**你的答案**：第六步失败会抛异常，抛异常就触发事务回滚，这次操作就失败

**评分**：✅ **完全正确**

**补充**：回滚靠的是 Spring AOP 代理——方法抛出异常时，代理拦截并执行 `ROLLBACK`，第 5 步的 `UPDATE` 一并撤销。

## 第 7 题 —— Mapper 接口没有实现类

**问**：MyBatis 的 Mapper 接口没有实现类，为什么能调？

**你的答案**：有 JDK 能动态代理

**评分**：✅ **正确，干脆利落**

**补充细节**

```
MyBatis 启动时扫描 @Mapper 接口
    → 用 JDK 动态代理生成实现类（必须接口才能代理）
    → 调用 decreaseBalance() 时，代理拦截
    → 用「namespace + 方法名」去 XML 里找同名 SQL
    → namespace = com.atm.mapper.AccountMapper
       id        = decreaseBalance
```

**这也是为什么 `@Param` 的名字必须和 `#{}` 完全一致** —— 参数名就是靠 `@Param` 传给 MyBatis 的。

## 第 8 题 —— 为什么要 Entity 转 DTO

**问**：为什么要 `TransRecord`（19 个字段）转成 `WithdrawResponse`（5 个字段），直接把实体返回不行吗？

**你的答案**：返回给用户不用全部字段都返回，比如密码，token 那些

**评分**：✅ **正确**

**补充专业化表述**

> 这是 **DTO 模式**：Entity 是数据库的镜像，DTO 是接口的形状。
> 两者分离，既能挡住敏感字段（密码哈希、内部 id、sessionId），
> 也能让接口和表结构**独立演进**（加字段不用改接口，改表不用改前端）。

## 第 9 题（补问）—— 去掉 WHERE 但保留 Java 判断

**问**：如果扣款 SQL 写成 `where id = #{id}`（去掉余额条件），但 Java 里保留 `if (rows == 0) throw 余额不足`，还会不会超扣？

**你的答案**：会，5 个并发同时进来的时候…

**评分**：⚠️ **结论对，原因要修正**

**正确原因**

```
去掉 WHERE 后 → 5 个请求的 UPDATE 全部执行成功
             → 每个请求的影响行数都是 1（不是 0）
             → if (rows == 0) 永远不成立
             → 这个判断变成【死代码】，一个都拦不住
             → 600 - 500×5 = -1900
```

**关键认知**：`rows == 0` 的拦截能力**完全来自** SQL 的 WHERE。
WHERE 一去，"余额不足"这个业务错误就再也不会抛出来了。

## 第 10 题（补问）—— 没有 `if (!mounted)`

**问**：`await apiPost(...)` 之后直接 `setState(...)`（没有 `if (!mounted)`），什么操作会让它报错？

**你的答案**：⏭️ 未答（说前端完全不懂）

**正确答案**

```
await 等网络的时候（可能几百毫秒到几秒）
    → 用户点了「退卡」/ 点了窗口 X / 按了 R 热重启
    → 界面被销毁，State 不再挂载
    → await 返回后代码继续执行 → 执行 setState
    → 报错：setState() called after dispose()
```

`mounted` = "这个 State 还挂在界面上吗"。这是 Flutter 提供的"对象是否还活着"的标志。
