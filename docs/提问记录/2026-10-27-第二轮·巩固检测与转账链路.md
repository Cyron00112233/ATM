# 第一部分：巩固检测（4 题）

## 检测 1 —— `setState` 反向理解

**问**：

```dart
onPressed: () { count++; }    // 不调 setState
```

点了 3 次这个按钮（屏幕一直显示 0），然后点一个有 `setState` 的按钮，屏幕显示几？

**你的答案**：3

**评分**：✅ **正确**

**为什么是 3**

```
点 3 次 → count 变成 3（变量真的变了），但 build() 没跑，屏幕还是 0
点 setState 按钮 → build() 重新执行
                → build() 里 Text('$count') 读的是【当前值】= 3
                → 屏幕显示 3（不是 +1 变 1，是直接跳到 3）
```

**关键认知（背下来）**

> **`setState` 不改数据，它只是"命令界面重新读一遍数据"。**
> **数据早就变了，屏幕只是停在上一帧。**

## 检测 2 —— 库存扣减是不是同一思路

**问**：库存扣减（商品库存）和余额扣减，是同一个思路吗？

**你的答案**：是。如果判断和修改不在同一个 SQL，有可能库存不够还仍然扣减，导致负数

**评分**：✅ **完全正确**

**通用表述（答辩、面试都能用）**

> 所有"有数量上限的资源"——余额、库存、优惠券、秒杀名额——
> 都用同一个解法：**把"数量够不够"写进 UPDATE 的 WHERE 里，靠影响行数判断成功与否。**

**这个问题的通用名字叫"超卖 / 超扣"。**

**你的答案**：不用

## 检测 4 —— Controller 自己 catch 了异常

**问**：如果 Controller 里自己写了 try-catch 把异常吞掉了，全局异常处理器还会生效吗？

**你的答案**：会

**评分**：❌ **错误**

**正确答案：不会生效。**

```java
// ❌ Controller 里自己吞掉异常
try {
    return Result.success("成功", atmService.withdraw(req));
} catch (Exception e) {
    return Result.fail(500, "出错了");     // ← 异常在这里被【消化】了
}
```

```
异常在 Controller 内部被 catch 住
    ↓
没有向外抛出（方法正常 return 了）
    ↓
@RestControllerAdvice 收不到任何异常
    ↓
全局异常处理器【完全不执行】
```

**全局异常处理器的原理：拦截"从 Controller 方法往外抛出的异常"。**
**异常一旦被 catch，就等于被吞了，外面不知道发生过什么。**

**这也是"Controller 不该写 try-catch"的深层原因**

```
① 写了 → 全局处理失效
② 错误格式不统一（有的走全局格式，有的自己拼）
③ 14 个接口要抄 14 遍，改提示要改 14 处
```

# 第二部分：转账链路（6 题）

## 第 1 题 —— 手续费三档

**问**：转账 100 / 1000 / 20000 元，手续费分别收多少？怎么算？

**你的答案**：100 收 1 元，1000 收 5 元，20000 收 50 元；手续费 = 金额 × 0.005，最低 1 元，最高 50 元

**评分**：✅ **完全正确**

**代码实现**（`AtmServiceImpl.calcFee`，第 635 行）

```java
private BigDecimal calcFee(BigDecimal amount) {
    BigDecimal fee = amount.multiply(new BigDecimal("0.005"))
            .setScale(2, RoundingMode.HALF_UP);      // 先按 0.5% 算，保留 2 位
    if (fee.compareTo(new BigDecimal("1")) < 0)  fee = new BigDecimal("1.00");   // 最低 1
    if (fee.compareTo(new BigDecimal("50")) > 0) fee = new BigDecimal("50.00");  // 最高 50
    return fee;
}
```

**三档验算**

| 转账金额 | × 0.005 | 夹在 [1, 50] 后 | 说明 |
|---|---|---|---|
| 100 | 0.50 | **1.00** | 不足最低，按 1 元收 |
| 1000 | 5.00 | **5.00** | 正常 |
| 20000 | 100.00 | **50.00** | 超最高，按 50 封顶 |

---

## 第 2 题 —— 为什么必须 BigDecimal

**问**：为什么手续费必须用 `BigDecimal`，不能用 `double`？

**你的答案**：用 double 会导致精度丢失，比如 0.1+0.2 它不会等于 0.3

**评分**：✅ **完全正确**

**补充：这个例子在金额场景下有多要命**

```dart
0.1 + 0.2 = 0.30000000000000004      // double 的真实结果
```

```
如果是 1000 元 × 0.005：
    double 可能算出 4.999999999999999
    存进数据库 decimal(12,2) 会被截成 4.99
    每笔少 1 分钱，一万笔就少 100 元，对不上账
```

**三个必须遵守的规矩**

```
① 金额用 BigDecimal，不用 double / float
② BigDecimal 比较大小用 compareTo()，不能用 == 或 equals()
     （equals 会比较 scale，"1000" 和 "1000.00" 不相等）
③ 除法必须指定精度和舍入方式：divide(x, 2, RoundingMode.HALF_UP)
```

## 第 3 题 —— 为什么记 3 条流水

**问**：转账为什么记 3 条流水？只记转出方 1 条行不行？

**你的答案**：方便对账，不行，只记转出方的话，那么转入方的钱哪里来的都不知道，还有手续费也会丢失

**评分**：✅ **正确**

**三条流水分别是什么**

| 流水类型 | 归属 | 金额 | 作用 |
|---|---|---|---|
| `TRANSFER_OUT` | 转出方 | 转账金额 | 转出方账单里能看到"转出 1000" |
| `FEE` | 转出方 | 手续费 | 手续费独立可查，便于对账 |
| `TRANSFER_IN` | **转入方** | 转账金额 | **收款方账单里能看到"收到 1000"** |

**你的理由很到位**："转入方的钱哪里都不知道" —— 这正是核心。

**余额链是自洽的（可用来验算）**

```
转账 1000、手续费 5：

TRANSFER_OUT   10000.00 → 8995.00     扣 1005（本金 + 手续费）
FEE             9000.00 → 8995.00     扣 5    ← 9000 = 10000 - 1000
TRANSFER_IN     5000.00 → 6000.00     加 1000
```

**三条串联起来能完整还原这笔交易 —— 这就是财务对账依赖的东西。**

## 第 4 题 —— `trans_no` 为什么加 F / I 后缀 ⚠️

**问**：3 条流水的 `trans_no` 为什么要加 `F` / `I` 后缀？

**你的答案**：不太清楚，我感觉是方便我看这是什么操作

**评分**：⚠️ **猜对了一半，但不是真正的原因**

**真正的原因：`trans_record.trans_no` 上有唯一索引**

```sql
unique key uk_trans_no (trans_no)
```

**如果 3 条流水都用同一个 `trans_no`：**

```
第 1 条 insert  trans_no = '20261027123456789012'   ✅ 成功
第 2 条 insert  trans_no = '20261027123456789012'   ❌ 撞唯一索引，插入失败
第 3 条 insert  trans_no = '20261027123456789012'   ❌ 同样失败
        ↓
整个事务回滚 → 转账失败
```

**所以必须让 3 条各不相同：**

```
20261027123456789012      → TRANSFER_OUT
20261027123456789012F     → FEE
20261027123456789012I     → TRANSFER_IN
                      ↑ F = Fee，I = In
```

**为什么 DB 层面设了唯一索引** —— 这是**幂等的兜底**：

```
同一笔交易重复提交（手抖点两次、网络重试）
    → 第二次 insert 会撞 uk_trans_no
    → 数据库直接拒绝 → 不会扣两次钱
```

**所以"加后缀"不是"方便看"，而是"唯一索引的硬性要求"。**
"方便看出是同一笔交易"只是附带的好处。

## 第 5 题 —— 为什么按 account_id 升序更新

**问**：为什么按 `account_id` 升序更新两方账户？不排序会出什么问题？

**你的答案**：让它们的账户 id 不同，不然两者并发的时候，比如 a+b 和 b+a，若加锁顺序相反会导致互相等待

**评分**：✅ **核心理解正确**（表述可以再精确一点）

**你的表述里有一处要改**：不是"让 id 不同"（id 本来就不同），而是**"让两个事务获取锁的顺序一致"**。

**精确表述**

```
场景：A(账户1) 转给 B(账户2)，同时 B 转到 A

【不排序】各自"先扣自己再加入对方"
    事务1：锁住账户1 → 等账户2
    事务2：锁住账户2 → 等账户1
    → 互相等待 → 死锁，数据库报 Deadlock found

【按 id 升序】两个事务都先拿账户1，再拿账户2
    事务1：拿到账户1 → 再拿账户2 → 完成
    事务2：等账户1释放 → 再拿到账户2 → 完成
    → 排队执行，不会死锁
```

**代码**

```java
if (fromAccount.getId() < toAccount.getId()) {
    // 先扣本方，再加入对方
    rows = accountMapper.decreaseBalance(fromAccount.getId(), total);
    ...
    accountMapper.increaseBalance(toAccount.getId(), amount);
} else {
    // 先加入对方，再扣本方
    accountMapper.increaseBalance(toAccount.getId(), amount);
    rows = accountMapper.decreaseBalance(fromAccount.getId(), total);
    ...
}
```

**通用规律（答辩、面试都能用）**

> **多个事务要锁多行时，只要所有事务都按同一顺序加锁，就不会形成环，也就不会死锁。**

## 第 6 题 —— 余额校验比的是什么

**问**：转账的余额校验，比的是 `amount` 还是 `amount + fee`？为什么？

**你的答案**：`amount + fee`，因为转账要手续费

**评分**：✅ **正确**（理由再补一层）

**为什么必须比 total，不能只比 amount**

```
卡里 1000 元，转 1000 元，手续费 5 元

【只比 amount】
    判断：1000 >= 1000 ✅ 通过
    实际扣款：decreaseBalance(id, 1005)
        → WHERE available_balance >= 1005 → 1000 >= 1005 不成立
        → 影响 0 行 → 抛"余额不足"
    → 用户会困惑："我明明有 1000，凭什么说余额不足？"

【比 total】
    判断：1000 >= 1005 ❌ 不通过
    → 提示"余额不足：转账 1000 元 + 手续费 5.00 元 = 1005.00 元"
    → 用户一下就明白差 5 块
```

**真正的扣款金额也是 `total`**

```java
BigDecimal total = amount.add(fee);
rows = accountMapper.decreaseBalance(fromAccount.getId(), total);   // ← 扣的是 total
```

**所以"判断金额"和"扣款金额"必须是同一个数，否则会出现"判断通过但扣款失败"的诡异提示。**
