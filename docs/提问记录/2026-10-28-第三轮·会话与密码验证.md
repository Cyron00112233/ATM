## Q2 —— 5 分钟超时怎么实现 ⚠️

**你的答案**：定义常量为 5，判断 `last.plusMinutes(SESSION_TIMEOUT_MINUTES).isBefore(LocalDateTime.now())`；每次操作后要把卡的状态改为超时，同时抛异常

**评分**：⚠️ 核心代码对了，但"每次操作后做什么"说反了

**你说对的部分** —— 超时判断的代码一字不差：

```java
// getValidSession()，L556-572
LocalDateTime last = session.getLastActiveTime() == null
        ? session.getLoginTime() : session.getLastActiveTime();
if (last != null && last.plusMinutes(SESSION_TIMEOUT_MINUTES).isBefore(LocalDateTime.now())) {
    atmSessionMapper.updateStatus(session.getId(), 3);   // 3 = 超时
    throw new BusinessException(ResultCode.UNAUTHORIZED,
            "会话已超时（5 分钟无操作），请重新插卡");
}
```

**你说反的部分：**

| 时机 | 做什么 |
|---|---|
| **每次操作成功后** | `updateLastActive(id)` 刷新 `last_active_time`（**不是**标记超时） |
| **每次请求开始时校验时** | 判断是否超时；**超时才** `updateStatus(id, 3)` 标记为超时 |

```
正常流程：
   插卡 → last_active = 10:00
   取款 → 刷新 last_active = 10:02
   查余额 → 刷新 last_active = 10:04
   （只要中间不停超过 5 分钟，会话一直有效）

超时流程：
   插卡 → last_active = 10:00
   （用户走开了 8 分钟）
   取款 → 校验：10:00 + 5分钟 = 10:05 < 10:08 → 超时
        → updateStatus(id, 3) 标记为超时
        → 抛 401「会话已超时，请重新插卡」
```

**两个动作要分清楚：**

```
刷新（updateLastActive）   → 每次成功操作都做
标记超时（updateStatus 3） → 只在检测到超时时做一次
```

## Q3 —— 交易密码怎么存的

**你的答案**：用 BCrypt 哈希存储；BCrypt 能生成随机盐让密码加密，彩虹表会失效，响应速度慢一点，加大别人破解密码的时间

**评分**：✅ **完全正确，三个理由都说到了**

**补充 BCrypt 的两个技术细节：**

```
① 盐是【随机】的，而且和哈希值存在一起
   同一个密码 123456，每次 encode 结果都不同：
       第 1 次：$2a$10$zJsrN0H6ntV2iimmiA5zAuXtoPyAk9cPNBJL0e2F47GcWUH26t5GC
       第 2 次：$2a$10$cqGTuUxQN9Etp9bSZE0aPefDwQ4vUj.YM.HBA9CM3S5uDqTb/pB2y
   → 所以不能用"查哈希表"的方式反推密码

② 慢是【故意】的
   cost = 10（2 的 10 次方 = 1024 轮运算），单次约 50~100ms
   正常登录感觉不到；但暴力破解每秒只能试 10~20 个
   → 破解成本从"几小时"变成"几百年"
```

**对比 MD5：**

| | MD5 | BCrypt |
|---|---|---|
| 速度 | 极快（每秒几亿次） | 慢（每秒几十次） |
| 盐 | 无（相同密码哈希相同） | 随机盐（每次不同） |
| 彩虹表 | 直接能查 | 失效 |
| 结论 | 不适合存密码 | ✅ 正确选择 |

## Q4 —— 错误次数为什么要原子自增

**你的答案**：原子自增，让数据库自己算，避免出现"读出来加一再写"的并发问题

**评分**：✅ **正确**（补一个具体场景）

**具体会丢成什么样：**

```sql
-- ❌ 危险写法
int count = user.getPwdErrorCount();      // 读到 1
count = count + 1;                        // 2
update bank_card set pwd_error_count = 2  // 写回 2
```

```
两个请求同时输错密码：
   请求A 读到 1
   请求B 读到 1
   请求A 写回 2
   请求B 写回 2          ← 覆盖了 A 的结果
   实际错了 2 次，数据库只记了 1 次
```

**正确写法（`BankCardMapper.xml` L19）：**

```sql
update bank_card
set pwd_error_count = pwd_error_count + 1     -- 数据库自己加
where id = #{id}
```

```
请求A 执行 → 1 + 1 = 2
请求B 执行 → 2 + 1 = 3        ← 排队，不丢
```

**这叫「丢失更新」问题**，和余额扣减的"超扣"是两类不同的并发问题：

| 并发问题 | 解法 |
|---|---|
| 超扣（判断 + 修改之间有窗口） | 把条件写进 WHERE |
| 丢失更新（读到旧值再写回） | 让数据库自己算（`x = x + 1`） |

## Q5 —— verifyPassword 为什么不能加事务 ⚠️ 重要订正

**你的答案**：防止抛业务异常会把"错误次数 +1""锁卡"一起回滚；加了的话会导致一次密码错误就锁卡

**评分**：⚠️ 前半完全正确，后半说反了

**你说对的部分** ✅：加了事务，抛业务异常会把"错误次数 +1"和"锁卡"一起回滚 —— 完全正确。

**你说反的部分** ❌：**不是"一次就锁卡"，而是"永远锁不了卡"。**

**完整推演：**

```
【加了 @Transactional】

第 1 次输错：
    increasePwdErrorCount  → count 0 → 1
    重新读取 errorCount = 1
    1 >= 3 ?  否
    抛 PASSWORD_ERROR(2004)          ← 业务异常
        ↓
    事务回滚 → count 回到 0          ← 白加了

第 2 次输错：count 0 → 1 → 回滚 → 0
第 3 次输错：count 0 → 1 → 回滚 → 0
第 100 次：  count 0 → 1 → 回滚 → 0

结论：errorCount 永远是 1，永远达不到 3 → 【永远锁不了卡】
```

**后果比"一次就锁"严重得多：**

```
用户可以写脚本无限次试密码
    → 6 位数字密码共 100 万种
    → 每秒试 10 次，约 28 小时暴力破解成功
    → 安全机制彻底失效
```

**这就是这个方法刻意不加事务的原因。**

**正确的表述（背下来）：**

> `verifyPassword` 不能加 `@Transactional`，因为它会抛业务异常。
> 加了事务，抛异常时会把"错误次数 +1"和"锁卡"一起回滚，
> 导致错误计数永远停在 1、卡片永远锁不上，用户可无限次暴力试密码。
> **这是"业务异常"与"事务回滚"冲突的典型案例。**

## Q6 —— verified 字段干什么用

**你的答案**：用来验密码的，之后才能允许取款等操作；不校验的话用户不用进行密码校验就可以直接进行一系列操作

**评分**：✅ **完全正确**

**补充背景**（这个字段是我们自己加上去的）：

```
原来的设计缺陷：
   atm_session 只有 status（1进行中/2已退卡/3超时）
   getValidSession() 只校验这三项
   → 插卡后不调 verify-password，直接调 /withdraw 也能成功取款！

修复方案：
   ① atm_session 加 verified 列（默认 0）
   ② 验密码成功后标记 verified = 1（AtmSessionMapper.markVerified）
   ③ 新增 getVerifiedSession()：在 getValidSession 基础上要求 verified == 1
   ④ 取款/存款/转账/余额/明细 全部改用 getVerifiedSession
```

**哪些接口用哪个：**

| 方法 | 用哪个校验 | 为什么 |
|---|---|---|
| 插卡 | 无（建立会话） | — |
| `verifyPassword` | `getValidSession` | 它必须在"未验证"状态下可用 |
| `ejectCard` | `getValidSession` | 退卡不需要验密码 |
| 取款 / 存款 / 转账 / 余额 / 明细 | **`getVerifiedSession`** | 资金操作必须先验密码 |

**这叫「会话双阶段校验」** —— 答辩时可以主动讲。

## Q7 —— 退卡后原 token 还能用吗 ❌ + 一个很好的疑问

**你的答案**：用户里面的余额还是之前的……上一次操作都不生效了，因为会话还是之前的。
**（然后你问：为什么用户还能拿原来的 token？）**

**评分**：❌ 结论不对，但你提的这个问题非常有价值

**先回答你的疑问：token 确实还在，但服务端不认了。**

**退卡时做了什么（`ejectCard`，L171）：**

```java
public void ejectCard(String sessionToken) {
    AtmSession session = getValidSession(sessionToken);
    atmSessionMapper.updateStatus(session.getId(), 2);   // ← 只改状态，不删记录
    log.info("退卡完成 sessionNo={}", session.getSessionNo());
}
```

```sql
update atm_session
set status = 2,                          -- 2 = 已退卡
    logout_time = case when 2 = 2 then now() else logout_time end
where id = #{id}
```

**关键：token 那行记录【没有被删除】，只是 `status` 从 1 变成了 2。**

**再用这个 token 调取款：**

```
getVerifiedSession(token)
    ↓
getValidSession(token)
    ↓
selectByToken(token)  → 查到了！（token 确实存在）
    ↓
检查 status：status == 2，不是 1
    ↓
抛 401「会话已结束，请重新插卡」        ← 取款被拒绝
```

**所以答案是：**

```
token 字符串   → 还存在数据库里（能查到）
会话           → 已失效（status != 1）
结果           → 取款被拒绝，返回 401
```

**为什么"只改状态不删记录"：**

```
① 留审计痕迹：谁在什么时间插卡、什么时间退卡、用的哪台机器
② 如果删了，就没法查"这张卡今天在 ATM001 上操作过几次"
③ 数据库表 atm_session 本身就是"会话日志"，不是"临时缓存"
```

**这就是"可主动失效"的实现方式** —— 不删令牌，改状态。JWT 做不到这一点（见 Q8）。

## Q8 —— ATM 改用 JWT 会有什么问题 ⚠️

**你的答案**：如果 ATM 用 JWT，那它只能校验身份，之前进行的一系列操作都没有记录下来，包括一些取款记录

**评分**：⚠️ 方向沾到一点，但没答到核心

**先纠正一点**："操作没记录"不是 JWT 的问题 —— **交易流水是写数据库的（`trans_record` 表），和用什么认证方式完全无关。**

**真正的核心原因：JWT 是「无状态」的，服务端无法让已签发的 token 提前失效。**

```
JWT 的工作方式：
   登录 → 服务端签名生成 token（里面写着 userId + 过期时间）
   → 把 token 交给客户端
   → 服务端【不保存】任何东西
   → 每次请求：验签名 + 看有没有过期，就完事了
```

**关键结论：**

```
服务端手里没有"token 列表"
→ 无法"作废某个 token"
→ 只能等它自然过期
```

**放到 ATM 场景，会出这些事：**

| 场景 | 用 JWT 会怎样 | 用 sessionToken 会怎样 |
|---|---|---|
| 用户点了「退卡」 | token 还有效，2 小时内还能取款 💥 | 改 status=2，立刻失效 ✅ |
| 卡片挂失 | 手上那个 token 还能用 💥 | 立刻失效 ✅ |
| 5 分钟无操作超时 | **做不到**（过期时间写死在 token 里）💥 | 靠 last_active_time 判断 ✅ |
| 换台机器继续操作 | 同一 token 到处能用 💥 | 一台机器一个会话 ✅ |

**所以两套机制的分工：**

```
管理端 → JWT
    · 内部人员，短有效期（2 小时）
    · 不需要"踢人"
    · 无状态，扩展性好（多台服务器不用共享会话）

ATM 端 → 数据库会话 token
    · 高安全场景
    · 必须能"立即失效"（退卡/挂失/超时）
    · 有状态，每次查库（性能代价可以接受，ATM 并发低）
```

**答辩标准表述：**

> "管理端用无状态 JWT，因为内部人员不需要强制下线；
> ATM 端用数据库会话，因为退卡、挂失、超时这些场景要求令牌**立即失效**，
> 而 JWT 一旦签发就无法撤回，只能等过期。这是按安全需求做的差异化选择。"
