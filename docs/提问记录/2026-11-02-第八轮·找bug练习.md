# 题 1（前端）—— `int.parse` 的坑 ⚠️

## 题目

```dart
Future<void> withdraw() async {
  final amount = int.parse(amountCtrl.text.trim());

  final r = await _call('/api/atm/withdraw', {
    'sessionToken': sessionToken,
    'amount': amount,
  });

  if (!r.ok) { _fail(r); return; }

  _goResult('取款成功，余额 ${r.data['balanceAfter']}');
}
```

## 你的答案

> 我哪里是 tryParse 而这里是 parse，这里我也不知道有什么区别，还有就是这里没做金额判断，当金额为 null 和金额小于零时会报错

**评分**：⚠️ 找到了差异点，但说不清后果

**你说对的：**
```
✅ 项目里是 int.tryParse，这里是 int.parse
✅ 这里没做金额判断
```

## 正确答案

### `parse` 和 `tryParse` 的区别

```dart
int.parse('500')      // → 500        ✅
int.parse('')         // → 💥 FormatException: Invalid radix-10 number
int.parse('abc')      // → 💥 FormatException
int.parse('500.5')    // → 💥 FormatException

int.tryParse('500')   // → 500        ✅
int.tryParse('')      // → null       ← 不崩，返回 null
int.tryParse('abc')   // → null
```

**一句话：**

```
parse     转换失败 → 抛异常 → 程序崩
tryParse  转换失败 → 返回 null → 你能自己处理
```

### 什么时候会触发（很常见的真实场景）

```
用户在金额框里【什么都没输】，直接点「确 认」
    ↓
amountCtrl.text 是 ''（空字符串）
    ↓
int.parse('') → 💥 FormatException
    ↓
整个 App 崩溃
```

**所以必须写成：**

```dart
final amount = int.tryParse(amountCtrl.text.trim());
if (amount == null || amount <= 0) {
  _goResult('请输入正确的金额');
  return;
}
```

**这正是项目里的真实写法 —— 你一直在用正确的方式，只是没意识到"为什么必须这样"。**

### 关于"没做金额判断"

**要分清两种判断：**

| 判断 | 谁负责 | 不做会怎样 |
|---|---|---|
| **格式**（是不是数字） | **前端必须做** | 崩（就是这道题的 bug） |
| **范围**（>0、100 倍数、≤5000） | **后端必须做**，前端最好也做 | 多一个来回，体验差 |

**项目里前端做了"null 或 <= 0"，没做"100 整数倍"** —— 靠后端拦。用户输入 150 会先发请求再收到错误提示。能接受，但不如前端先拦。

# 题 2（后端）—— `@Transactional` 加在会抛业务异常的方法上 ✅

## 题目

```java
@Override
@Transactional(rollbackFor = Exception.class)          // ← 问题在这一行
public void verifyPassword(VerifyPasswordRequest request) {

    AtmSession session = getValidSession(request.getSessionToken());
    BankCard card = bankCardMapper.selectByCardNo(session.getCardNo());
    checkCardStatus(card);

    if (!passwordEncoder.matches(request.getPassword(), card.getPassword())) {
        bankCardMapper.increasePwdErrorCount(card.getId());
        int errorCount = bankCardMapper.selectByCardNo(card.getCardNo()).getPwdErrorCount();

        if (errorCount >= 3) {
            bankCardMapper.lockCard(card.getId());
            throw new BusinessException(ResultCode.CARD_LOCKED, "密码连续错误 3 次，卡片已锁定");
        }
        throw new BusinessException(ResultCode.PASSWORD_ERROR, "密码错误，还可尝试 " + (3 - errorCount) + " 次");
    }

    bankCardMapper.resetPwdErrorCount(card.getId());
    atmSessionMapper.markVerified(session.getId());
}
```

## 你的答案

> 这个方法是密码验证的，按理说不应该做事务回滚，做了会导致密码错误一次就抛异常，触发事务回滚，这样错误次数一直在 0-1 之间，一直锁不了卡，同时别人也能一直试错

**评分**：✅ **完全正确（这是五道题里答得最准的一道）**

## 正确答案

**加了 `@Transactional` 之后：**

```
第 1 次输错：
    increasePwdErrorCount  → count: 0 → 1
    errorCount = 1，未达 3
    抛 PASSWORD_ERROR(2004)              ← 业务异常（RuntimeException）
        ↓
    代理拦截到异常 → ROLLBACK
        ↓
    count 回到 0                          ← 白加了

第 2 次：0 → 1 → 回滚 → 0
第 100 次：0 → 1 → 回滚 → 0

结论：计数永远在 0~1 之间，永远到不了 3
     → 【永远锁不了卡】
     → 用户可无限次暴力试密码
     → 安全机制彻底失效
```

**答辩表述（背下来）：**

> "`verifyPassword` 抛的是业务异常（RuntimeException），加了 `@Transactional` 后抛异常会回滚，
> 导致'错误次数 +1'和'锁卡'一起被撤销，计数永远在 0~1 之间，卡片永远锁不上，
> 用户可以无限次暴力试密码。所以这个方法刻意不加事务。"

**这是"注解很方便，但要知道它包住了什么"的典型例子。**

# 题 3（后端）—— 条件更新缺了 WHERE 余额判断 ✅

## 题目

```xml
<update id="decreaseBalance">
    update account
    set available_balance = available_balance - #{amount},
        balance           = balance - #{amount}
    where id = #{id}
</update>
```

```java
int rows = accountMapper.decreaseBalance(account.getId(), amount);
if (rows == 0) {
    throw new BusinessException(ResultCode.BALANCE_NOT_ENOUGH);
}
```

## 你的答案

> SQL 语句哪里没有做 available_balance - #{amount} 判断，当这个小于零时会报错，rows == 0 这个判断不成立，会导致可以一直取款，就算余额变成负数也没有问题，因为不会抛异常出去

**评分**：✅ 结论对，一处要修正

**你说对的：**
```
✅ 缺了余额判断
✅ rows == 0 永远不成立
✅ 可以一直取款，余额变负数也不抛异常
```

**要修正的**：你说"当这个小于零时会报错" —— **不会报错。**

## 正确答案

**少了这一行：**

```xml
and available_balance >= #{amount}
```

**后果链条：**

```
WHERE 里只有 id = #{id}
    ↓
id 一定存在 → 每条 UPDATE 都匹配 1 行
    ↓
rows 恒等于 1（不是 0）
    ↓
if (rows == 0) throw 余额不足;   ← 变成【死代码】，永远不执行
    ↓
余额 600，5 个人各取 500 → 全部成功
    ↓
余额 600 - 2500 = -1900      💥 但没有任何报错
```

**为什么"不报错"更可怕：**

```
MySQL 的 decimal 字段允许负数
表上也没有 CHECK 约束
    ↓
扣到 -1900 也【静默成功】，一行错误日志都没有
    ↓
只有对账时才发现
```

**顺带：并发下也会超扣**（这正是第二轮那个 5 并发实验结果演示的场景）。

# 题 4（后端）—— 转账没按 account_id 排序 ✅

## 题目

```java
@Override
@Transactional(rollbackFor = Exception.class)
public TransferResponse transfer(TransferRequest request) {
    ... 校验省略 ...

    // ★ 先扣本方，再加入对方
    int rows = accountMapper.decreaseBalance(fromAccount.getId(), total);
    if (rows == 0) {
        throw new BusinessException(ResultCode.BALANCE_NOT_ENOUGH);
    }
    accountMapper.increaseBalance(toAccount.getId(), amount);

    ... 记流水、组装响应 ...
}
```

## 你的答案

> 在扣款的时候应该按照账户 ID 大小执行，不然会导致死锁，平时就你一个人转账，而当两个人同时转账的时候，就会导致相互等待程序执行不起来

**评分**：✅ **完全正确**

## 正确答案

**死锁机制：**

```
A(账户1) → B(账户2)   同时   B(账户2) → A(账户1)

不排序（都"先扣自己再加入对方"）：
    事务1：锁住账户1 → 等账户2
    事务2：锁住账户2 → 等账户1
        ↓
    循环等待 → MySQL 检测到死锁 → 强制回滚其中一个
        ↓
    报错：Deadlock found when trying to get lock; try restarting transaction
```

**为什么"平时测不出来"：**

```
必须三个条件同时成立：
    ① 两个用户同时转账
    ② 方向相反（A→B 和 B→A）
    ③ 两个事务的时间窗口【重叠】（毫秒级）

自己测试时只有一个用户在操作 → 条件①不成立 → 100% 正常
```

**更麻烦：运维也很难发现**

```
用户看到"系统异常，请重试"
重试一次就成功了（这次没撞上）
→ 用户不报 bug，日志里只有一条 Deadlock，容易被忽略
```

**修复：**

```java
if (fromAccount.getId() < toAccount.getId()) {
    decreaseBalance(fromId, total);
    increaseBalance(toId, amount);
} else {
    increaseBalance(toId, amount);
    decreaseBalance(fromId, total);
}
```

**通用规律：**
> **多个事务要锁多行时，只要所有事务都按同一顺序加锁，就不会形成环，也就不会死锁。**

# 题 5（后端）—— FEE 流水金额写错 ✅

## 题目

```java
// ② 手续费 FEE
TransRecord feeRecord = new TransRecord();
feeRecord.setTransNo(transNo + "F");
feeRecord.setTransTypeCode("FEE");
feeRecord.setAmount(amount);            // ← 问题在这一行
feeRecord.setBeforeBalance(fromAccount.getAvailableBalance().subtract(amount));
feeRecord.setAfterBalance(fromAfter);
transRecordMapper.insert(feeRecord);
```

## 你的答案

> ② 是记录手续费的流水，金额应该记录 fee 而不是 amount，这样不会让程序出错，也不会让转账金额出错，但到时候对账的时候会发现账有问题

**评分**：✅ **完全正确**

## 正确答案

**具体算一下：**

```
转账 1000，手续费 5

正确：
    TRANSFER_OUT   amount=1000   fee=5
    FEE            amount=5      fee=0
    TRANSFER_IN    amount=1000   fee=0
    → 手续费收入合计 = 5

实际（bug）：
    FEE            amount=1000   fee=0
    → 手续费收入合计 = 1000      ← 虚增 200 倍
```

**对账时的连锁后果：**

```
① 日终轧账：手续费总收入对不上
② 统计报表：手续费收入异常高（单笔看不出）
③ 账户余额完全正确（流水只是记录，不参与扣款）
④ 交易金额、余额链全对 —— 只有"手续费"这一项错
```

**这叫「记录错误」而不是「交易错误」：钱没错，账错了。**

## ⚠️ 出题时我自己的话不严谨（自我修正）

**我在题目里说"界面上也看不出来" —— 这句不准确。**

**严格说：明细页能看到那条"手续费 1000.00"，但：**

```
· 它不报错
· 它不影响余额
· 普通用户看到"手续费 1000 元"会觉得奇怪，但多半以为是显示问题
· 只有对账 / 统计分析时才会真正暴露
```

**准确说法：不报错、不影响主流程，容易被忽略；真正暴露是在对账时。**

# 三道题的难度阶梯（值得记）

```
题 1：用错 API      → 运行时崩溃        能立刻发现
题 2：多加一个注解  → 安全机制静默失效   表面正常，功能没生效
题 3：少一个 WHERE  → 静默扣成负数      数据错了，没有任何报错

难度递增的原因：
    崩溃     → 你马上知道出事了
    静默失效 → 表面上一切正常
    静默出错 → 数据悄悄错了，几个月后才发现
```

**真实项目里最可怕的不是崩溃，是第三种。**

**你抓到了第二种和第三种（题 2、题 3、题 5）—— 说明对"静默失效"这类问题很敏感，这是很好的直觉。**
