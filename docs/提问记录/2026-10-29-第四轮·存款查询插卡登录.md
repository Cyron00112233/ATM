## Q1 —— 存款和取款的 3 处差异

**你的答案**：取款需要余额查询，存款不用；取款是钞箱出账，存款是钞箱进账；组装返回的东西不一样

**评分**：✅（两处核心答对了，第三处不是关键）

**真实的 3 处核心差异**（对照 `withdraw` 和 `deposit`）：

| | 取款 | 存款 |
|---|---|---|
| **① 账户操作** | `decreaseBalance(id, amount)`<br>带 `where available_balance >= amount`<br>**看返回行数，0 行 = 余额不足** | `increaseBalance(id, amount)`<br>**无条件、不看返回行数** |
| **② 钞箱操作** | `decreaseNoteCount(id, n)`<br>**先校验 `noteCount < need100`** | `increaseNoteCount(id, n)`<br>**只校验钞箱存在，不校验数量** |
| **③ 单笔上限** | 5000（`validateAmount`） | **10000**（`validateDepositAmount`） |

**你说对了 ① 和 ② 的方向，"组装返回的东西不同"是附带差异，不是核心。**

**另外两处小差异：**

```
流水类型：WITHDRAW  vs  DEPOSIT
afterBalance：availableBalance.subtract(amount)  vs  .add(amount)
```

## Q2 —— 存款为什么不需要余额校验 ⚠️

**你的答案**：因为存款是把钱存进去，而取款需要从余额里面取钱，这个不知道

**评分**：⚠️ 前半对，后半（钞箱差异）没答

**前半 ✅**：存款是 `balance + amount`，加钱永远不会"不够"，所以不需要条件校验。

**后半（钞箱的差异）：**

```
【取款】先查钞箱，再校验张数够不够
    AtmCashBox box100 = selectByDeviceAndDenomination(deviceNo, 100);
    if (box100 == null || box100.getNoteCount() < need100) {
        throw CASH_NOT_ENOUGH("ATM 现金不足，请换台机器或改取其他金额");
    }
    decreaseNoteCount(box100.getId(), need100);      // 扣钞

【存款】只校验钞箱存不存在，不校验数量
    AtmCashBox box100 = selectByDeviceAndDenomination(deviceNo, 100);
    if (box100 == null) {
        throw CASH_NOT_ENOUGH("该机具暂不支持存款");   // 只需要"有钞箱"
    }
    increaseNoteCount(box100.getId(), noteCount);     // 加钞
```

**核心规律：**

> **"减少"要校验够不够，"增加"不需要校验够不够。**
>
> 这条规律同时适用于余额和钞箱 —— 取款的两处"减少"都要校验，存款的两处"增加"都不需要。

## Q3 —— 只读操作为什么不需要事务

**你的答案**：因为它们都只是读操作，不会涉及金额的一些问题，就比如不会出现取款时取 500 而钞箱没钱导致用户钱丢失

**评分**：✅ **正确**

**更精确的表述：**

> `@Transactional` 的作用是"多条修改要么全成、要么全回滚"。
> **只读操作没有"修改"，就没有"回滚"这回事**，加了事务只会白白多一次事务开启/提交的开销。

**你举的例子方向对**（取款时钞箱不够导致钱丢了）—— 那正是"部分成功"的风险，而余额查询/明细**压根不会修改任何数据**，不存在这个风险。

## Q4 —— `Math.min(limit, 50)` ⚠️ 重要混淆

**你的答案**：从 50 和 limit 里面取一个最小值，**让手续费不超过 50**。不加的话有可能导致手续费超过 50，同时如果前端传一个很大的数，会导致数据库返回很多行，占用很多内存

**评分**：⚠️ 结论对，但**把两个不同的 "50" 混在一起了**

**这是这一轮最需要纠正的地方。**

**项目里有两个完全无关的 50：**

| | 位置 | 含义 |
|---|---|---|
| **手续费封顶 50** | `calcFee()`，L635 | 转账手续费最多收 50 元 |
| **明细查询上限 50** | `queryTransactions()`，L363 | 一次最多查 50 条流水 |

**两者没有任何关系** —— 一个是钱，一个是记录条数。

**`Math.min(limit, 50)` 的真正作用：**

```java
// queryTransactions()，L363 附近
int lim = (limit == null || limit <= 0) ? 10 : Math.min(limit, 50);
List<TransRecord> records = transRecordMapper.selectByCardNo(cardNo, lim);
```

```
不加上限的后果（你自己也答到了）：
   前端传 limit = 999999
       ↓
   SQL: select ... from trans_record where card_no = ? limit 999999
       ↓
   把这张卡的全部历史流水（可能几十万条）一次性加载到内存
       ↓
   ① 数据库压力大   ② 内存可能爆   ③ 接口响应慢到超时
       ↓
   恶意用户可以用这一个请求拖垮服务（一种简单的 DoS）
```

**这叫"分页上限保护"或"接口限流"，是后端开发的常规操作。**

**一句话记：**

> **凡是"要多少条由前端决定"的接口，后端都必须有一个硬上限。**

## Q6 —— `sessionToken` 怎么生成的 ⚠️

**你的答案**：它先用一个会话把这次进行的操作都存进去，比如 token、机器设备号，最后把这段对话放在 Mapper 里面，存进数据库里面

**评分**：⚠️ 流程描述对了，但**没有回答"怎么生成"**

**真实生成方式：**

```java
// insertCard()，L78 附近
String sessionNo = UUID.randomUUID().toString().replace("-", "");   // 32 位
String token     = UUID.randomUUID().toString().replace("-", "");   // 32 位

AtmSession session = new AtmSession();
session.setSessionNo(sessionNo);
session.setCardNo(card.getCardNo());
session.setDeviceNo(deviceNo);
session.setToken(token);
session.setStatus(1);           // 1 = 进行中
atmSessionMapper.insert(session);
//  useGeneratedKeys="true" → 插入后自增 id 会回填到 session.id
```

**两个关键点：**

```
① token = UUID 去掉横线 → 32 位十六进制字符串
     例：9ae3fc3cf909406885d4c36476f2c3ff
     · 随机性足够（2^122 种可能，无法猜）
     · 不包含任何业务信息（不是 JWT 那种自包含的）

② session_no 和 token 是两个不同的东西
     session_no → 给人看的编号（审计、客服查会话用）
     token      → 给程序用的凭证（客户端每次请求带它）
```

**你描述的"存进数据库"这部分 ✅ 是对的** —— `insert atm_session`。

## Q7 —— 登录失败提示为什么统一 ⚠️

**你的答案**：防止用户知道是哪个地方错误就不断去试错；分开的话，用户知道密码错了而用户名没错就会一直试密码，有可能导致服务器崩溃，同时安全性也降低了

**评分**：⚠️ 方向对（防枚举），但风险描述不准

**这个攻击的名字叫「用户枚举」（User Enumeration）**

```
如果分开提示：

  输入 admin + 错误密码   → "密码错误"        ← 泄露：admin 这个用户【存在】
  输入 asdfg + 任意密码   → "用户不存在"      ← 泄露：asdfg 这个用户【不存在】

攻击者拿一个常见用户名列表跑一遍：
   能得到【系统里有哪些管理员账号】的完整名单
        ↓
   然后只针对这些真实账号爆破密码（效率提升几百倍）
        ↓
   也知道了系统装了多少人、有没有超级管理员
```

**统一提示之后：**

```
输入 admin + 错误密码   → "用户名或密码错误"    ← 什么信息都没泄露
输入 asdfg + 任意密码   → "用户名或密码错误"    ← 完全一样
```

**你说"服务器崩溃"不准确** —— 真正的风险是**信息泄露 + 爆破效率提升**，不是把服务器打崩。

**正确表述：**

> "登录失败时，'用户不存在'和'密码错误'返回同一句提示，防止**用户枚举攻击**。
> 否则攻击者可以先探测出系统里存在哪些账号，再针对性地爆破密码。"

## Q8 —— JWT 里放什么，为什么不放更多

**你的答案**：放了用户 ID、用户名字和角色；因为 JWT 是 Base64 编码不是加密，任何人拿到 token 都可以解开看里面写了什么，会导致用户的真实信息暴露

**评分**：✅ **完全正确**

**代码（JwtUtil）：**

```java
Jwts.builder()
    .subject(String.valueOf(userId))          // sub = 用户 id
    .claim("username", username)              // 自定义字段
    .claim("role", role)                      // 角色
    .issuedAt(new Date())
    .expiration(new Date(System.currentTimeMillis() + expire))
    .signWith(key)                            // 签名（防篡改）
    .compact();
```

**你说的原理完全正确：**

```
JWT 的组成：header.payload.signature
              ↑        ↑         ↑
            base64    base64    签名
                      ↑
              这一段【只是 Base64 编码】，不是加密
              任何人拿 token 去 base64decode 就能看到明文
```

**随手就能解开的例子：**

```
eyJzdWIiOiIxIiwidXNlcm5hbWUiOiJhZG1pbiIsInJvbGUiOiJhZG1pbiIsImlhdCI6MTc5Mjg5MzA1NSwiZXhwIjoxNzkyODk2NjU1fQ
     ↓ base64 解码
{"sub":"1","username":"admin","role":"admin","iat":1792893055,"exp":1792896655}
```

**所以三个结论：**

```
① JWT 里【绝不能放】密码、身份证号、手机号、余额这些敏感数据
② JWT 的签名只保证"没被篡改"，不保证"内容保密"
③ 要保密 → 用 HTTPS 传输（防止中途被截获）
```

**这句话可以放在答辩里：**

> "JWT 的 payload 是 Base64 编码而非加密，任何人都能解开，
> 所以只放 userId、username、role 这些非敏感信息，
> 敏感数据一律不放。"

# 一个额外的观察（超出题目范围，但值得知道）

**看取款/存款的流水组装：**

```java
record.setBeforeBalance(account.getAvailableBalance());
record.setAfterBalance(account.getAvailableBalance().subtract(amount));
//                                             ↑ 用的是【读出来的旧值】
```

**并发下 `beforeBalance` / `afterBalance` 可能不准** —— 因为 `account` 是第 4 步读出来的快照，第 5 步扣款后并没有重新读。

真实银行的做法是：
```
扣款后重新查一次余额（select again）
或者用 update ... returning（PostgreSQL）
或者把余额变更记成独立的事件流
```

**这是本项目的一个已知局限**，不影响演示，但答辩如果老师追问"并发时流水里的余额准不准"，可以这样答：

> "流水的 before/after 余额取自扣款前的查询结果，
> 在极高并发下可能与实际值有偏差。生产环境应该在扣款后重新查询余额、
> 或使用 `SELECT ... FOR UPDATE` 加锁读取。本期为简化实现采用的方案。"
