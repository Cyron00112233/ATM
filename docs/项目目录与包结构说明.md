# 项目目录与包结构说明

> 每个包/目录是干什么的、里面有哪些文件、为什么不能合并。
> 最后附「新增一个功能要动哪些文件」的清单。

---

# 一、整体结构

```
atm/
├── atm-server/            后端（Spring Boot）
│   ├── src/main/java/com/atm/      ← Java 代码（10 个包）
│   ├── src/main/resources/         ← 配置文件 + SQL 映射
│   └── src/test/                   ← 测试
│
├── atm-app/               前端（Flutter）
│   ├── lib/               ← Dart 代码（2 个文件）
│   └── test/              ← 测试
│
└── docs/                  文档与 SQL 脚本
```

**后端代码分成 10 个包，按"职责"划分：**

```
com.atm
├── AtmServerApplication.java   启动类
├── common/        全局基础设施（响应格式、异常、错误码）
├── config/        装配（Bean 注册、拦截器注册）
├── interceptor/   拦截器（JWT 校验）
├── controller/    接口入口（管 HTTP）
├── dto/           接口的进出口形状（管数据格式）
├── service/       业务接口（管"做什么"）
│   └── impl/      业务实现（管"怎么做"）
├── mapper/        数据访问接口（管"取什么数据"）
├── entity/        数据库表实体（管"数据长什么样"）
└── util/          工具类
```

# 二、每个包的详细说明

## 1. `com.atm`（根目录）—— 启动类

| 文件 | 行数 |
|---|---|
| `AtmServerApplication.java` | 13 |

**干什么**：整个程序的入口。`main()` 方法一跑，Spring Boot 就启动。

```java
@SpringBootApplication
public class AtmServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(AtmServerApplication.class, args);
    }
}
```

`@SpringBootApplication` 这一行做了三件事：

```
① 自动配置（看 classpath 有什么依赖，自动装配）
② 组件扫描（扫描 com.atm 及其子包，找 @Controller/@Service/@Mapper）
③ 标记为配置类
```

**注意**：启动类必须放在**最外层包**（`com.atm`），因为它扫描的是**自己所在的包及子包**。如果放到 `com.atm.controller` 里，`com.atm.service` 就扫不到了。

## 2. `common` —— 全局基础设施（5 个文件）

| 文件 | 行数 | 作用 |
|---|---|---|
| `Result.java` | 65 | 统一响应外壳 `{code, message, data, timestamp}` |
| `ResultCode.java` | 52 | 错误码枚举（200/400/1001/2001/2005…） |
| `BusinessException.java` | 36 | 业务异常（Service 主动抛，带 code + message） |
| `GlobalExceptionHandler.java` | 91 | 全局异常处理（`@RestControllerAdvice`） |
| `UserContext.java` | 34 | ThreadLocal 保存"当前登录的管理员" |

**干什么**：这些东西**不属于任何一条业务流程**，而是**所有流程都要用**的公共设施。

**三个必须理解的点：**

**① `Result` 是所有接口的返回值外壳**

```java
Result.success("取款成功", response)        // → {code:200, message:"取款成功", data:{...}}
Result.fail(ResultCode.BALANCE_NOT_ENOUGH)  // → {code:2001, message:"余额不足", data:null}
```

**好处**：前端只需要判断 `code == 200`，不用区分"HTTP 200 但业务失败"这种情况。

**② `BusinessException` 是 Service 的"退货方式"**

```java
if (rows == 0) {
    throw new BusinessException(ResultCode.BALANCE_NOT_ENOUGH);   // 不 return 错误对象，直接抛
}
```

**为什么抛异常而不是返回错误对象**：

```
返回错误对象 → 每个调用方都要判断"是不是错误"，容易漏
抛异常       → 正常流程一条直线走到底，出问题直接中断到全局处理器
```

**③ `UserContext` 用 ThreadLocal 传"当前用户"**

```
拦截器解析 JWT → 拿到 userId → UserContext.set(userId, username)
                                    ↓（同一个线程）
Service 里 → UserContext.getUserId()  就能拿到
                                    ↓
请求结束 → afterCompletion → UserContext.clear()   ← 必须清理
```

**为什么必须 `clear()`**：Tomcat 用**线程池**，线程会被复用。不清理的话，下一个请求可能拿到上一个用户的身份（**串号**，严重安全问题）。

**④ 为什么这个包不能合并到 controller**

```
如果把这些类放到 controller 包里：
   Service 想抛 BusinessException，就得 import com.atm.controller.BusinessException
   → Service 依赖了 Controller 层的东西 → 分层被打穿
   → 以后 Controller 层重构，Service 跟着炸
```

**common 和 config 是"谁都能依赖、自己不依赖别人"的底层包。**

## 3. `config` —— 装配（2 个文件）

| 文件 | 行数 | 作用 |
|---|---|---|
| `SecurityConfig.java` | 28 | 注册 `BCryptPasswordEncoder` Bean |
| `WebMvcConfig.java` | 28 | 注册登录拦截器 + 路径白名单 |

**干什么**：告诉 Spring "我要这些工具"、"拦截器要拦哪些路径"。

**`SecurityConfig` 全文就一个 Bean：**

```java
@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

注册后，任何地方 `@Autowired PasswordEncoder` 就能用：

```
passwordEncoder.encode("123456")                   → 生成 BCrypt 哈希
passwordEncoder.matches("123456", 数据库里的哈希)   → 校验，返回 boolean
```

**`WebMvcConfig` 是拦截器的配置：**

```java
registry.addInterceptor(loginInterceptor)
        .addPathPatterns("/api/**")                    // 拦所有 /api 开头
        .excludePathPatterns(                          // 但排除这些
                "/api/admin/login",     // 登录接口本身
                "/api/atm/**",          // ATM 端用 sessionToken，不走 JWT
                "/api/hello",           // 健康检查
                "/error"                // Spring 默认错误页
        );
```

**⚠️ 最容易误解的一点**：`/api/atm/**` 被**排除**了，意味着 ATM 接口**完全不校验 JWT**。

**但"不校验 JWT" ≠ "不设防"** —— ATM 接口在 Service 层用 `sessionToken` 自己校验（`getVerifiedSession`）。

**两个包（config / common）的区别：**

```
common   = "业务代码要用的东西"（Result、异常）
config   = "Spring 装配相关的东西"（Bean、拦截器注册）
```

## 4. `interceptor` —— 拦截器（1 个文件）

| 文件 | 行数 | 作用 |
|---|---|---|
| `LoginInterceptor.java` | 85 | 解析 JWT，校验通过后把用户存进 `UserContext` |

**干什么**：在请求进入 Controller **之前**，先检查有没有登录。

**执行时机：**

```
请求进来
    ↓
拦截器 preHandle()   ← 这里校验 JWT
    ↓ （true = 放行）
Controller 方法
    ↓
拦截器 afterCompletion()   ← 这里清理 UserContext
    ↓
响应返回
```

**三个关键实现：**

**① 取 token**

```java
String header = request.getHeader("Authorization");    // "Bearer eyJhbGciOi..."
if (header == null || !header.startsWith("Bearer ")) {
    return reject(response, "未登录，请先登录");
}
String token = header.substring(7).trim();             // 去掉 "Bearer " 前缀
```

**② 验签 + 过期**

```java
try {
    Claims claims = jwtUtil.parseToken(token);         // 验签 + 检查过期，失败会抛异常
    Long userId = Long.valueOf(claims.getSubject());
    UserContext.set(userId, username);
    return true;                                       // 放行
} catch (Exception e) {
    return reject(response, "登录已过期，请重新登录");
}
```

**③ 为什么这里要手动写 JSON（重点）**

```java
private boolean reject(HttpServletResponse response, String message) throws Exception {
    response.setStatus(401);
    response.setContentType("application/json;charset=UTF-8");
    response.getWriter().write("{\"code\":401,\"message\":\"" + message + "\",\"data\":null}");
    return false;                                      // false = 拦截
}
```

**因为拦截器在 Controller 之前执行，此时还没进入 Spring 的处理链** —— `@RestControllerAdvice` 接不到这里的异常，所以只能手动往响应流里写 JSON。

**这也是"为什么 Q4 那种 Controller 自己 catch 会让全局处理器失效"的同一类原因：异常没被抛到该去的地方。**

## 5. `controller` —— 接口入口（4 个文件）

| 文件 | 行数 | 接口数 | 是否校验 JWT |
|---|---|---|---|
| `HelloController.java` | 28 | 1 | ❌ |
| `AdminController.java` | 33 | 1 | ❌（登录本身） |
| `CustomerController.java` | 58 | 4 | ✅ |
| `AtmController.java` | 107 | 8 | ❌（用 sessionToken） |

**干什么**：**只管 HTTP 收发**，三件事：

```java
@PostMapping("/withdraw")
public Result<WithdrawResponse> withdraw(@Valid @RequestBody WithdrawRequest request) {
    return Result.success("取款成功", atmService.withdraw(request));
}
//   ↑ 路由          ↑ 参数校验      ↑ 转成对象      ↑ 包统一外壳
```

**三个注解的作用：**

| 注解 | 作用 |
|---|---|
| `@PostMapping("/withdraw")` | 这个路径 + POST 方法 → 走这个方法 |
| `@RequestBody` | 把 JSON 字符串反序列化成 Java 对象 |
| `@Valid` | 触发 `WithdrawRequest` 上的校验注解（`@NotNull`、`@DecimalMin`…） |

**Controller 里绝对不做的三件事：**

```
❌ 不写业务判断（余额够不够、卡能不能用）→ 归 Service
❌ 不碰数据库（不出现 Mapper）          → 归 Service
❌ 不写 try-catch                      → 归 GlobalExceptionHandler
```

**为什么 Controller 这么薄**：它只是"HTTP 到 Java 的翻译层"。所有逻辑都在 Service，这样以后要加"手机银行取款"，可以直接复用 Service，不用碰 HTTP 那一层。

## 6. `dto` —— 接口的进出口形状（16 个文件）

| 类型 | 文件 |
|---|---|
| **请求体**（前端 → 后端） | `LoginRequest`、`InsertCardRequest`、`VerifyPasswordRequest`、`EjectCardRequest`、`WithdrawRequest`、`DepositRequest`、`BalanceRequest`、`TransDetailRequest`、`TransferRequest` |
| **响应体**（后端 → 前端） | `LoginResponse`、`InsertCardResponse`、`WithdrawResponse`、`DepositResponse`、`BalanceResponse`、`TransDetailItem`、`TransferResponse` |

**干什么**：定义"接口收什么、给什么"。

**请求 DTO 上带校验注解：**

```java
@Data
public class WithdrawRequest {
    @NotBlank(message = "会话令牌不能为空")
    private String sessionToken;

    @NotNull(message = "取款金额不能为空")
    @DecimalMin(value = "100", message = "取款金额最少100元")
    @DecimalMax(value = "5000", message = "单笔取款最多 5000 元")
    private BigDecimal amount;
}
```

Controller 上的 `@Valid` 一触发，这些注解就生效。校验不通过 → 抛 `MethodArgumentNotValidException` → 全局处理器接住 → 返回 400 + 具体提示。

**注意：`@DecimalMin` 只能限制上下限，"是不是 100 的整数倍"这种规则表达不了** —— 所以要放在 Service 的 `validateAmount()` 里。

**为什么不直接用 Entity 接、用 Entity 返回（重点）：**

| | Entity（数据库镜像） | DTO（接口形状） |
|---|---|---|
| `TransRecord` | **19 个字段**（含 accountId / sessionId / deviceNo） | `TransDetailItem` **只有 9 个** |
| `SysUser` | 有 `password`（BCrypt 哈希） | `LoginResponse` **没有 password** |
| 变化原因 | 加索引要加字段 | 前端需求变了要加字段 |

**两个作用：**
1. **安全**：密码哈希、内部 id 绝不返回给前端
2. **解耦**：数据库加字段不影响接口，接口改字段不影响表

## 8. `mapper` —— 数据访问接口（7 个文件）

| 文件 | 行数 | 对应 XML |
|---|---|---|
| `CustomerMapper.java` | 26 | `CustomerMapper.xml` |
| `SysUserMapper.java` | 18 | `SysUserMapper.xml` |
| `BankCardMapper.java` | 24 | `BankCardMapper.xml` |
| `AccountMapper.java` | 29 | `AccountMapper.xml` |
| `AtmSessionMapper.java` | 27 | `AtmSessionMapper.xml` |
| `AtmCashBoxMapper.java` | 24 | `AtmCashBoxMapper.xml` |
| `TransRecordMapper.java` | 24 | `TransRecordMapper.xml` |

**干什么**：定义"要用到哪些 SQL"，但**只写接口，不写实现**。

```java
@Mapper
public interface AccountMapper {
    int decreaseBalance(@Param("id") Long id, @Param("amount") BigDecimal amount);
}
```

**没有 `AccountMapperImpl`** —— MyBatis 用 **JDK 动态代理**在运行时生成实现类。

**接口方法名怎么和 SQL 对应上：**

```
接口全限定名  com.atm.mapper.AccountMapper
              ↓ 对应
XML 的 namespace="com.atm.mapper.AccountMapper"

方法名        decreaseBalance
              ↓ 对应
XML 的 id="decreaseBalance"
```

**为什么方法参数要加 `@Param`（踩过的坑）：**

```java
// ❌ XML 里用 #{deviceNo}，接口写 @Param("device")
int selectByDeviceAndDenomination(@Param("device") String device, ...);
// 报错：Parameter 'deviceNo' not found. Available parameters are [device, param1, ...]

// ✅ 名字必须完全一致
int selectByDeviceAndDenomination(@Param("deviceNo") String device, ...);
```

**单参数时可以不写 `@Param`，多参数时必须写**（否则 MyBatis 用 `param1`、`param2` 命名）。

## 9. `service` + `service/impl` —— 业务层（6 个文件）

| 文件 | 行数 | 职责 |
|---|---|---|
| `AdminService.java` | 12 | 接口（登录） |
| `AdminServiceImpl.java` | 74 | 实现 |
| `CustomerService.java` | 23 | 接口（客户查询） |
| `CustomerServiceImpl.java` | 47 | 实现 |
| `AtmService.java` | 45 | 接口（8 个 ATM 方法声明） |
| **`AtmServiceImpl.java`** | **614** | **核心业务实现（占后端代码 1/4）** |

**为什么接口和实现要分开：**

```java
// Controller 依赖接口，不依赖实现
private final AtmService atmService;    // ← 类型是接口

// 好处：
// ① 以后换实现（比如加缓存版）Controller 一行不改
// ② 单元测试可以 mock 接口，不用启动数据库
// ③ 团队分工：甲写接口，乙写实现
```

**`AtmServiceImpl` 是整个项目最重的类，8 个方法：**

| 方法 | 干什么 | 加事务 |
|---|---|---|
| `insertCard()` | 插卡建会话 | ⭕ 可加可不加 |
| `verifyPassword()` | 验密码 + 连错锁卡 | ❌ **绝不能加** |
| `ejectCard()` | 退卡 | ⭕ |
| `withdraw()` | 取款 | ✅ **必须** |
| `deposit()` | 存款 | ✅ **必须** |
| `transfer()` | 转账 | ✅ **必须** |
| `queryBalance()` | 余额查询 | ❌ 只读 |
| `queryTransactions()` | 交易明细 | ❌ 只读 |

**为什么 `verifyPassword` 不能加事务**：它抛业务异常，加了事务会把"错误次数 +1"和"锁卡"一起回滚 → 卡片永远锁不上 → 用户可无限试密码。

**这个包承担了全部业务规则：**

```
金额是否是 100 的整数倍       → validateAmount()
手续费怎么算                 → calcFee()
卡状态能不能用               → checkCardStatus()
会话有没有超时               → getValidSession()
有没有验过密码               → getVerifiedSession()
流水号怎么生成               → generateTransNo()
卡号怎么脱敏                 → maskCardNo()
```

**Controller 和 Service 的分工（一句话）：**

```
Controller：把 HTTP 请求变成一个 Java 对象，再调 Service，再把结果包成 HTTP 响应
Service  ：拿到对象，做业务判断，调 Mapper，控事务，返回结果对象或抛异常
```

## 10. `util` —— 工具类（1 个文件）

| 文件 | 行数 | 作用 |
|---|---|---|
| `JwtUtil.java` | 84 | 签发 / 解析 JWT |

**干什么**：和一个业务无关的通用能力。

**两个方法：**

```java
// 签发：把 userId、username、role 塞进 token 并签名
String token = jwtUtil.generateToken(1L, "admin", "admin");

放 util 表示"谁都能用，但不属于任何业务"
```

# 三、`resources` 目录

| 文件 | 行数 | 作用 |
|---|---|---|
| `application.properties` | 29 | 数据库连接、MyBatis 配置、JWT 密钥 |
| `mapper/*.xml`（7 个） | 275 | **真正的 SQL 都写在这里** |

**`application.properties` 的四组配置：**

```properties
# ① 数据库连接
spring.datasource.url=jdbc:mysql://localhost:3306/atm_db?...
spring.datasource.username=root
spring.datasource.password=123456

# ② MyBatis
mybatis.type-aliases-package=com.atm.entity     # 让 XML 里 resultType 可以写简名
mybatis.mapper-locations=classpath:mapper/*.xml # XML 在哪
mybatis.configuration.map-underscore-to-camel-case=true  # available_balance → availableBalance
mybatis.configuration.log-impl=org.apache.ibatis.logging.stdout.StdOutImpl  # 打印 SQL

# ③ 服务器
server.port=8080

# ④ 自定义配置
atm.jwt.secret=...
atm.jwt.expire=7200000    # 2 小时
```

**为什么 SQL 不写在 Java 里**：

```
写在 Java（注解方式 @Select）  → 长 SQL 难读、难格式化、改一个条件要改注解
写在 XML                    → 有高亮、有缩进、支持 <if> <where> 动态 SQL
```

**XML 的结构：**

```xml
<mapper namespace="com.atm.mapper.AccountMapper">     ← 绑定接口

    <select id="selectByCardId" resultType="com.atm.entity.Account">
        select ... from account where card_id = #{cardId}
    </select>                                          ← 对应接口方法名

    <update id="decreaseBalance">
        update account
        set available_balance = available_balance - #{amount},
            balance           = balance - #{amount}
        where id = #{id}
          and available_balance >= #{amount}           ← 余额校验
    </update>
</mapper>
```

**`#{}` 和 `${}` 的区别（面试常问）：**

```
#{xxx}  → 预编译参数（PreparedStatement 的 ?），防 SQL 注入 ✅
${xxx}  → 字符串直接拼接，有注入风险 ❌
```

**项目里全部用 `#{}`。**

# 四、前端目录

| 文件 | 行数 | 作用 |

**前端的"分层"比后端简单得多，就两层：**

```
main.dart  →  界面层（对应后端 Controller + Service 的活）
api.dart   →  网络层（对应后端 Mapper 的活：只管"怎么拿到数据"）
```

**为什么前端不需要那么细的分层：**

```
后端要防：并发、事务、SQL 注入、越权 → 必须严格分层
前端只是：显示界面 + 发请求          → 分两层就够
```

# 五、一次请求怎么穿过这些包

**以「取款 500」为例：**

```
【前端】lib/main.dart
    withdraw()  →  _call()  →  lib/api.dart: apiPost()
                                    ↓
════════════════════ HTTP POST /api/atm/withdraw ════════════════════
                                    ↓
【后端】config/WebMvcConfig
    检查路径 /api/atm/** 在白名单 → 不经过 interceptor/LoginInterceptor
                                    ↓
controller/AtmController
    ④ withdraw(@Valid @RequestBody WithdrawRequest)
        · @RequestBody + Jackson：JSON → WithdrawRequest 对象
        · @Valid：触发参数校验（金额 100~5000）
        · 调用 service
                                    ↓
service/impl/AtmServiceImpl
    withdraw(WithdrawRequest)
        · ① getVerifiedSession()     校验会话 + 验密码
        · ② checkCardStatus()        校验卡状态
        · ③ validateAmount()         100 整数倍、金额范围
        · ④ accountMapper.selectByCardId()
        · ⑤ accountMapper.decreaseBalance()   ★ 扣钱
        · ⑥ cashBoxMapper.decreaseNoteCount() ★ 扣钞
        · ⑦ transRecordMapper.insert()        ★ 记流水
        · ⑧ atmSessionMapper.updateLastActive()
                                    ↓
mapper/*.java（接口）
    MyBatis 动态代理拦截 → 找同名 SQL
                                    ↓
resources/mapper/*.xml
    <update id="decreaseBalance"> ... </update>
                                    ↓
【数据库】MySQL
    update account set available_balance = available_balance - 500
    where id = 1 and available_balance >= 500
                                    ↓
【返回】service → WithdrawResponse → controller → Result → Jackson → JSON
                                    ↓
════════════════════ HTTP 200 + JSON ════════════════════
                                    ↓
【前端】apiPost 返回 ApiResult → withdraw() 拿到 → _goResult() → setState → 界面刷新
```

**异常路径（任何一步抛 BusinessException）：**

```
Service 抛异常
    ↓
Spring AOP 事务代理捕获 → ROLLBACK（撤销前面已执行的 SQL）
    ↓
异常继续抛给 Controller → Controller 不接
    ↓
common/GlobalExceptionHandler 接住
    ↓
包成 Result{code, message, data:null} → Jackson → 返回前端
```

# 六、命名规律（一眼看出文件干什么）

| 后缀 | 位置 | 含义 |
|---|---|---|
| `XxxApplication` | 根 | 启动类 |
| `XxxController` | controller | HTTP 入口 |
| `XxxService` | service | 业务接口 |
| `XxxServiceImpl` | service/impl | 业务实现 |
| `XxxMapper`（.java） | mapper | 数据访问接口 |
| `XxxMapper`（.xml） | resources/mapper | 真正的 SQL |
| `Xxx`（无后缀） | entity | 数据库表实体 |
| `XxxRequest` | dto | 请求体 |
| `XxxResponse` / `XxxItem` | dto | 响应体 |
| `XxxUtil` | util | 工具类 |
| `XxxConfig` | config | 装配配置 |

**记住这张表，看到文件名就知道它属于哪一层、大概干什么。**

# 七、新增一个功能要动哪些文件

**假设要加一个「修改交易密码」功能（`POST /api/atm/change-password`）：**

```
① dto/ChangePasswordRequest.java        新建  请求体（sessionToken + 旧密码 + 新密码）
② dto/ChangePasswordResponse.java       新建  （可省，返回 void 也行）

③ service/AtmService.java               改    加一行方法声明
④ service/impl/AtmServiceImpl.java      改    写实现（校验旧密码 → BCrypt 加密新密码 → update）

⑤ mapper/BankCardMapper.java            改    加方法声明（updatePassword）
⑥ resources/mapper/BankCardMapper.xml   改    写 SQL

⑦ controller/AtmController.java         改    加一个 @PostMapping 方法
```

**共 7 处（2 新建 + 5 修改）。**

**这个顺序就是开发的思考顺序：**

```
先想"前端要传什么"（dto）
  → 再想"业务要做几步"（service 接口）
    → 再想"要读写哪些表"（mapper）
      → 最后写 SQL（xml）
        → 最后暴露成接口（controller）
```

**注意：Service 接口和实现都要改，XML 和 Mapper 接口都要改 —— 成对出现，漏一个就报错。**

# 八、一页纸速查

```
层级          包                 职责              不该做的事
──────────────────────────────────────────────────────────────────
入口          controller         HTTP 收发          不写业务、不碰 DB、不 try-catch
业务接口      service            定义能力           —
业务实现      service/impl       业务规则 + 事务     不碰 HTTP
数据访问      mapper + xml       读写数据库         不做业务判断
数据形状      entity             表结构镜像         不给前端看
              dto                接口形状           不含业务逻辑
基础设施      common             响应/异常/错误码   不依赖任何业务包
装配          config             Bean / 拦截器      不写业务
拦截          interceptor        JWT 校验           —
工具          util               通用能力           —
```

**一句话总结：**

> **controller 管 HTTP，service 管业务，mapper 管 SQL，entity 管表结构，dto 管接口形状，
> common 管全局，config 管装配。各管一摊，互不越界。**
