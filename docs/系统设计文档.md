# 一、设计目标与约束

## 1.1 目标

| # | 目标 | 衡量方式 |
|---|---|---|
| 1 | 覆盖 ATM 机具端完整业务闭环 | 插卡 → 验密 → 取款/存款/转账/查询 → 退卡 全流程可演示 |
| 2 | 交易数据必须准确 | 任何失败都不能造成账实不符 |
| 3 | 并发下不超扣、不重复扣 | 多请求并发时余额不为负、流水不重复 |
| 4 | 安全可验证 | 不验密码不能交易；卡片可锁定；会话可失效 |
| 5 | 代码可讲解 | 每个设计都能说出"为什么" |

## 1.2 非目标（本期明确不做）

```
管理端界面、统计报表、日终轧账、电子凭条
日累计限额、单日次数限制
分布式部署 / 多机具共享会话
```

## 1.3 约束

| 约束 | 影响 |
|---|---|
| 单机部署 | 不需要分布式锁、不需要会话共享 |
| 无 Redis / MQ | 并发控制必须靠数据库能力（行锁、唯一索引） |
| 面向答辩演示 | 优先"说得清"而不是"功能多" |
| 数据量小 | 不需要分页优化、不需要缓存 |

**关键设计推论：**

> 因为没有 Redis 和 MQ，**所有并发控制必须落到数据库层**（条件更新、原子自增、唯一索引、加锁顺序）。
> 这反而让设计更简单 —— 不引入中间件，就少了一整类故障点。

# 二、总体设计

## 2.1 架构分层

```
Controller   →  只管 HTTP 收发（参数绑定、校验触发、包统一响应）
Service      →  业务规则 + 流程编排 + 事务边界
Mapper       →  数据访问（接口 + XML SQL）
MySQL        →  数据与并发控制
```

**分层的目的不是"看起来规范"，而是解决四个具体问题：**

| 问题 | 不分层会怎样 | 分层后 |
|---|---|---|
| 复用 | 手机银行取款要抄 60 行业务逻辑 | 直接调同一个 Service 方法 |
| 事务范围 | 事务包住 JSON 解析，连接占用变长 | 事务只在 Service 方法上 |
| 单测 | 测"余额不足"要启动 Web 容器 | 直接 new Service 测 |
| 定位 | 改需求不知道改哪个文件 | 业务 → Service，SQL → Mapper |

## 2.2 技术选型及理由

| 选型 | 理由 | 不用什么 / 为什么 |
|---|---|---|
| Spring Boot 3.5 | 内嵌 Tomcat + 自动配置，`main()` 直接跑 | 不用传统 SSM：省掉 web.xml + 5 个 XML 配置 |
| MyBatis | SQL 可控，复杂条件好写 | 不用 JPA：金额扣减需要精确控制 SQL |
| MySQL 8 InnoDB | 支持事务 + 行锁 | 不用 MyISAM：没有事务 |
| BCrypt | 随机盐 + 故意慢 | 不用 MD5：可查表、无盐 |
| jjwt 0.12 | 轻量，只要签发/验签 | 不用 Spring Security 全家桶：它会拦截所有接口，本项目要自己控制白名单 |
| BigDecimal | 精确小数 | 不用 double：0.1+0.2≠0.3 |
| Flutter | 一套代码跑 Windows 桌面 | 不用 Web：机具端是桌面程序 |

## 2.3 一次请求的数据流

```
前端按钮
  → main.dart: withdraw()
  → api.dart: apiPost()           拼 URL、jsonEncode
════════ HTTP POST /api/atm/withdraw ════════
  → (拦截器：/api/atm/** 在白名单，跳过)
  → AtmController.withdraw()      @Valid 校验 + 转发
  → AtmServiceImpl.withdraw()     ★ @Transactional 开启
      ① getVerifiedSession      会话 + 验密码
      ② checkCardStatus         卡状态
      ③ validateAmount          金额规则
      ④ selectByCardId          查账户
      ⑤ decreaseBalance         ★ 扣钱（WHERE 带余额校验）
      ⑥ decreaseNoteCount       ★ 扣钞
      ⑦ insert TransRecord      ★ 记流水
      ⑧ updateLastActive        刷新会话
════════ MySQL ════════
      正常 → COMMIT   /   异常 → ROLLBACK
  → WithdrawResponse → Result → JSON
════════ HTTP 200 ════════
  → 前端 setState → 界面刷新
```

## 3.1 会话与认证：为什么两套机制

### 问题

管理员和 ATM 用户都在"登录"，能不能用同一套认证？

### 设计思路

**不能 —— 因为两者的安全需求相反。**

| | 管理端 | ATM 端 |
|---|---|---|
| 使用者 | 内部人员 | 任意持卡人 |
| 会话时长 | 2 小时 | 5 分钟无操作 |
| 是否需要"立即踢下线" | 不需要 | **必须**（退卡、挂失、超时） |
| 是否多端同时在线 | 可以 | 不行（一机一会话） |

### 方案对比

| 方案 | 能否立即失效 | 多机扩展 | 结论 |
|---|---|---|---|
| 全用 JWT | ❌ 不能（签发后无法撤回） | ✅ 好 | ATM 端不可行 |
| 全用数据库会话 | ✅ 能 | ❌ 每台机都要查库 | 管理端没必要 |
| **分开用** | 各自满足 | 管理端无状态 | ✅ **采用** |

### 实现

```
管理端：JWT（无状态）     → LoginInterceptor 验签 → UserContext
ATM 端：atm_session 表    → getValidSession / getVerifiedSession 查库
```

## 3.2 插卡建会话

### 问题

插卡时要拒绝哪些卡？会话怎么建立？

### 设计思路

**插卡是"建立会话"而不是"验证身份"** —— 密码在后面单独验证。

所以要做的只有三件事：**校验卡能不能用 → 建立会话 → 返回脱敏信息**。

### 实现（`insertCard`）

```
① 按 cardNo 查 bank_card，查不到 → 1002
② checkCardStatus(card)：
     status=2 → 2005「卡片已锁定（时间），请联系银行解锁」
     status=3 → 2006「卡片已挂失」
     status=4 → 2006「卡片已注销」
③ 校验 expire_date（为 null 表示长期有效）
④ 查 customer 拿姓名
⑤ 生成 session_no 和 token（都是 UUID 去横线，32 位）
⑥ insert atm_session（status=1，verified=0）
```

### 关键代码

```java
String sessionNo = UUID.randomUUID().toString().replace("-", "");
String token     = UUID.randomUUID().toString().replace("-", "");
atmSessionMapper.insert(session);   // useGeneratedKeys 回填自增 id
```

### 两个设计点

**① `session_no` 和 `token` 为什么是两个东西**

```
session_no → 给人看的编号（审计、客服查会话、日志）
token      → 给程序用的凭证（客户端每次请求带它）
```

**② 为什么不直接返回卡号明文**

```
返回 6222********0001
理由：屏幕可能被别人看到；脱敏后仍能识别是哪张卡
```

## 3.3 交易密码验证与锁卡

### 问题

密码怎么存？连续错怎么锁？并发下错误次数会不会丢？

### 设计思路

**三个子问题，三个手段：**

| 子问题 | 手段 |
|---|---|
| 密码怎么存 | BCrypt（随机盐 + 故意慢） |
| 连续 3 次锁卡 | 错误计数 + 达到阈值改卡状态 |
| 并发下计数不丢 | **原子自增**（数据库自己加） |

### 为什么密码用 BCrypt 不用 MD5

| | MD5 | BCrypt |
|---|---|---|
| 速度 | 每秒几亿次 | 每秒几十次（故意慢，cost=10） |
| 盐 | 无 → 相同密码哈希相同 | 随机盐 → 每次哈希都不同 |
| 彩虹表 | 直接能查 | 失效 |
| 暴力破解 | 几小时 | 几百年 |

### 为什么错误次数必须"原子自增"

```sql
-- ❌ 危险：读出来 → 加一 → 写回
int count = card.getPwdErrorCount();   // 读到 1
card.setPwdErrorCount(count + 1);      // 2
update ... set pwd_error_count = 2;    // 写回 2

-- 两个请求同时失败：
--   A 读到 1，B 读到 1
--   A 写 2，B 写 2          ← B 覆盖了 A，实际错 2 次只记 1 次
```

```sql
-- ✅ 正确：让数据库自己加
update bank_card set pwd_error_count = pwd_error_count + 1 where id = #{id}
-- A 执行 → 2
-- B 执行 → 3        ← 排队，不丢
```

**这叫「丢失更新」问题** —— 和余额超扣是两类不同的并发问题（超扣是"判断和修改分离"，丢失更新是"读旧值再写回"）。

### 实现（`verifyPassword`）

```
① getValidSession（只校验会话，不要求 verified —— 它本身就是来验密码的）
② 查卡 + checkCardStatus
③ BCrypt.matches(明文, 哈希)
   ├─ 失败 → increasePwdErrorCount（原子 +1）
   │         重新读最新值
   │         ├─ >= 3 → lockCard（card_status=2, lock_time=now）→ 抛 2005
   │         └─ < 3  → 抛 2004，提示"还可尝试 N 次"
   └─ 成功 → resetPwdErrorCount（归零）
④ markVerified（标记会话已验证）
⑤ updateLastActive
```

### ⭐ 这个模块最重要的设计：**不能加 `@Transactional`**

```java
@Override
// ❌ 绝对不能写 @Transactional
public void verifyPassword(VerifyPasswordRequest request) { ... }
```

**加了会怎样（这是本项目最关键的一个反直觉设计）：**

```
第 1 次输错：
    increasePwdErrorCount → count: 0 → 1
    errorCount = 1，未达 3
    抛 PASSWORD_ERROR(2004)              ← 业务异常
        ↓
    事务回滚 → count 回到 0              ← 白加了

第 2 次：0 → 1 → 回滚 → 0
第 100 次：0 → 1 → 回滚 → 0

结论：计数永远在 0~1 之间，永远到不了 3 → 【永远锁不了卡】
     → 用户可无限次暴力试密码 → 安全机制彻底失效
```

**结论：业务异常 + 事务回滚 = "已完成的数据变更被撤销"，在这个场景下是灾难。**

> 如果既需要事务又需要抛业务异常，必须配 `@Transactional(noRollbackFor = BusinessException.class)`。
> 本项目的选择是"干脆不加事务"，因为这几步本来就不需要"一起成功"。

## 3.4 会话双阶段校验（`verified`）

### 问题

插卡只是建会话，还没验密码。**不验密码能不能直接取款？**

### 发现的问题（开发过程中自查发现）

```
原设计：atm_session 只有 status（1进行中/2已退卡/3超时/4异常）
        getValidSession() 只校验这三项
        ↓
        插卡后不调 verify-password，直接调 /withdraw 也能成功取款  💥
```

### 设计思路

**给会话加"是否已验证密码"的标志，形成两个阶段：**

```
阶段 1：插卡      → 建会话（status=1, verified=0）
                  此时只能调 verify-password / eject-card
阶段 2：验密码成功 → 标记 verified=1
                  此时才能做资金操作
```

### 实现

| 步骤 | 内容 |
|---|---|
| 1 | `atm_session` 加列 `verified tinyint not null default 0` |
| 2 | `AtmSession` 实体加 `verified` 字段 |
| 3 | Mapper 加 `markVerified(id)`；`selectByToken` 列出 `verified` |
| 4 | `verifyPassword` 成功后调 `markVerified` |
| 5 | 新增 `getVerifiedSession()`：在 `getValidSession` 基础上要求 `verified == 1` |
| 6 | 取款/存款/转账/余额/明细 改用 `getVerifiedSession` |

```java
private AtmSession getVerifiedSession(String token) {
    AtmSession session = getValidSession(token);          // 先做全套会话校验
    if (session.getVerified() == null || session.getVerified() != 1) {
        throw new BusinessException(ResultCode.UNAUTHORIZED, "请先验证交易密码");
    }
    return session;
}
```

### 哪些接口用哪个校验

| 方法 | 校验方式 | 为什么 |
|---|---|---|
| `insertCard` | 无 | 它负责建立会话 |
| `verifyPassword` | `getValidSession` | 必须在"未验证"状态下可用 |
| `ejectCard` | `getValidSession` | 退卡不需要验密码 |
| 取款 / 存款 / 转账 / 余额 / 明细 | **`getVerifiedSession`** | 资金操作必须先验密码 |

## 3.5 取款

### 问题

一次取款动了三张表（账户、钞箱、流水）。任何一步失败，怎么保证不出现"钱扣了但没出钞"？

### 设计思路

**两个不同的问题，两个不同的手段，不能混：**

| 问题 | 手段 | 为什么 |
|---|---|---|
| 余额不够却扣成了负数 | **SQL 条件更新**（`where available_balance >= amount`） | 判断和修改必须是一个原子动作 |
| 钱扣了但没出钞 | **`@Transactional`** | 三张表要么全成、要么全回滚 |

### 实现（`withdraw`，9 步）

```
① getVerifiedSession          会话 + 验密码
② checkCardStatus             卡状态
③ validateAmount              100 整数倍 / 100~5000
④ selectByCardId              查账户 + 校验账户状态
⑤ decreaseBalance             ★ 扣钱：返回 0 行 = 余额不足
⑥ 配钞：need100 = amount/100
   box100 == null || noteCount < need100 → 抛 2007（事务回滚，⑤ 的扣款撤销）
   decreaseNoteCount          ★ 扣钞
⑦ insert TransRecord          ★ 记流水（WITHDRAW）
⑧ updateLastActive            刷新会话
⑨ 组装 WithdrawResponse
```

### 关键代码

```java
// ⑤ 扣钱：条件更新，返回 0 行就是余额不足
int rows = accountMapper.decreaseBalance(account.getId(), amount);
if (rows == 0) {
    throw new BusinessException(ResultCode.BALANCE_NOT_ENOUGH);
}
```

```xml
<update id="decreaseBalance">
    update account
    set available_balance = available_balance - #{amount},
        balance           = balance - #{amount}
    where id = #{id}
      and available_balance >= #{amount}     ← ★ 判断和修改在同一条 SQL 里
</update>
```

### 金额校验设计（`validateAmount`）

```
① null 或 <= 0        → 2003 金额不合法
② 不是 100 的整数倍    → 2003（提示"取款金额必须是 100 的整数倍"）
③ 大于 5000           → 2002 超出限额
```

**为什么没有单独判断"至少 100 元"？**

```
条件 A：amount > 0
条件 B：amount 是 100 的整数倍
A + B ⇒ 最小的正数是 100 ⇒ "至少 100" 是推导出来的，不需要单独判断
```

**为什么判断顺序重要（`5050` 的例子）：**

```
先判 100 倍数 → 5050 不是 → 报 2003（金额不合法）
先判 > 5000   → 5050 是   → 报 2002（超出限额）
```

**本项目选择"先判格式，再判范围"** —— 格式错误比超限更根本。

## 3.6 存款

### 问题

存款和取款看起来对称，但有几处**必须不对称**。

### 设计思路：一条通用规律

> **"减少"要校验够不够，"增加"不需要校验够不够。**

### 实现差异对照

| | 取款 | 存款 |
|---|---|---|
| 账户操作 | `decreaseBalance(id, amount)`<br>带 `where available_balance >= amount`<br>**看返回行数** | `increaseBalance(id, amount)`<br>**无条件、不看返回行数** |
| 钞箱操作 | `decreaseNoteCount(id, n)`<br>**先校验 `noteCount < need100`** | `increaseNoteCount(id, n)`<br>**只校验钞箱存在** |
| 单笔上限 | 5000 | **10000** |
| 流水类型 | `WITHDRAW` | `DEPOSIT` |
| afterBalance | `balance.subtract(amount)` | `balance.add(amount)` |

### 存款也必须加事务

虽然"加钱"本身不会失败，但它仍然动了 **3 张表**（账户、钞箱、流水）。

```
如果加钱成功、记流水失败 → 余额多了但账上没记录 → 对不上账
所以仍然需要事务保证"一起成功"
```

## 3.7 转账（最复杂的模块）

### 问题

一笔转账要：扣转出方、加转入方、扣手续费、记流水。四个子问题：

| # | 问题 | 设计手段 |
|---|---|---|
| 1 | 手续费怎么算 | `amount × 0.005`，夹在 [1, 50]，用 BigDecimal |
| 2 | 两边更新怎么保证一致 | 同一个 `@Transactional` |
| 3 | A→B 与 B→A 并发会死锁 | **按 `account_id` 升序更新** |
| 4 | 双方账单都要能查到 | **记 3 条流水** |

### 手续费的设计演进（四步）

```java
// 第 1 版：最直观（逻辑已正确，但有精度和隐式截断的风险）
double fee = amount * 0.005;
if (fee < 1)  fee = 1;
if (fee > 50) fee = 50;

// 第 2 版：换 BigDecimal（double 存 0.005 会变成 0.005000000000000000104…）
BigDecimal fee = amount.multiply(new BigDecimal("0.005"));   // 注意：传字符串不传 double

// 第 3 版：显式控制小数位（不依赖数据库隐式截断）
.setScale(2, RoundingMode.HALF_UP)

// 第 4 版：夹上下限（compareTo 不能写成 <  >）
if (fee.compareTo(ONE) < 0)  fee = new BigDecimal("1.00");
if (fee.compareTo(FIFTY) > 0) fee = new BigDecimal("50.00");
```

**三档验算：**

| 转账金额 | × 0.005 | 实际收取 |
|---|---|---|
| 100 | 0.50 | **1.00**（不足最低） |
| 1000 | 5.00 | **5.00**（正常） |
| 20000 | 100.00 | **50.00**（超最高） |

### 防死锁的设计

**问题场景：**

```
A(账户1) → B(账户2)   同时   B(账户2) → A(账户1)

如果都"先扣自己再加入对方"：
    事务1：锁住账户1 → 等账户2
    事务2：锁住账户2 → 等账户1
    → 互相等待 → 死锁
```

**解决方案：统一加锁顺序**

```java
if (fromAccount.getId() < toAccount.getId()) {
    decreaseBalance(fromId, total);
    if (rows == 0) throw 余额不足;
    increaseBalance(toId, amount);
} else {
    increaseBalance(toId, amount);
    rows = decreaseBalance(fromId, total);
    if (rows == 0) throw 余额不足;
}
```

> **通用规律：多个事务要锁多行时，只要所有事务都按同一顺序加锁，就不会形成环，也就不会死锁。**

### 为什么记 3 条流水

| 流水 | 归属 | 金额 | 作用 |
|---|---|---|---|
| `TRANSFER_OUT` | 转出方 | 转账金额 | 转出方账单能看到"转出 1000" |
| `FEE` | 转出方 | 手续费 | 手续费独立可查，便于对账 |
| `TRANSFER_IN` | **转入方** | 转账金额 | **收款方账单能看到"收到 1000"** |

**如果只记 1 条（转出方）：**

```
① 收款方的账单里查不到这笔收入 → 用户投诉"我的钱哪来的？"
② 手续费没有独立记录 → 无法单独核对手续费收入
```

### `trans_no` 为什么要加 `F` / `I` 后缀

```sql
-- trans_record 表上有唯一索引
unique key uk_trans_no (trans_no)
```

```
3 条流水用同一个 trans_no：
   第 1 条 insert ✅
   第 2 条 insert ❌ 撞唯一索引 → 插入失败
   第 3 条 insert ❌ 同样失败
   → 整个事务回滚 → 转账失败
```

```
20261027123456789012      → TRANSFER_OUT
20261027123456789012F     → FEE
20261027123456789012I     → TRANSFER_IN
```

**为什么 DB 层要设唯一索引** —— 这是**幂等兜底**：

```
手抖点两次「确认」/ 网络重试
    → 第二次 insert 撞 uk_trans_no
    → 数据库直接拒绝 → 不会扣两次钱
```

### 余额链自洽（可用于验算）

```
转账 1000、手续费 5：

TRANSFER_OUT   10000.00 → 8995.00     扣 1005（本金 + 手续费）
FEE             9000.00 → 8995.00     扣 5    ← 9000 = 10000 - 1000
TRANSFER_IN     5000.00 → 6000.00     加 1000
```

**三条串联能完整还原这笔交易 —— 这就是财务对账依赖的东西。**

### 余额校验为什么比 `amount + fee`

```
卡里 1000，转 1000，手续费 5

【只比 amount】判断 1000 >= 1000 ✅ 通过
              实际扣款 decreaseBalance(id, 1005)
              → WHERE 1000 >= 1005 不成立 → 0 行 → 抛"余额不足"
              → 用户困惑："我明明有 1000"

【比 total】   判断 1000 >= 1005 ❌ 不通过
              → 提示"余额不足：转账 1000 + 手续费 5.00 = 1005.00 元"
```

**判断金额和扣款金额必须是同一个数**，否则会出现"判断通过但扣款失败"的诡异提示。

## 3.8 余额查询与交易明细

### 为什么只读操作不加 `@Transactional`

```
@Transactional 的作用是"多条修改要么全成、要么全回滚"
只读操作没有"修改"，就没有"回滚"这回事
加了只会白白多一次事务开启/提交的开销
```

### 交易明细的设计要点

**① 分页上限保护**

```java
int limit = (request.getLimit() == null || request.getLimit() <= 0)
        ? 10
        : Math.min(request.getLimit(), 50);
```

```
不加上限的后果：
    前端传 limit = 999999
    → 一次查出全部历史流水（可能几十万条）
    → 数据库压力 + 内存爆 + 响应超时
    → 恶意用户一个请求就能拖垮服务（简单 DoS）

通用规则：
    凡是"要多少条由前端决定"的接口，后端都必须有硬上限
```

> ⚠️ **注意区分两个"50"**：手续费封顶 50（钱）vs 明细上限 50（条数）—— **完全无关**。

**② 交易类型中文名的翻译**

```java
private static final Map<String,String> TRANS_TYPE_NAMES = Map.of(
    "WITHDRAW", "取款", "DEPOSIT", "存款",
    "TRANSFER_OUT", "转账转出", "TRANSFER_IN", "转账转入",
    "FEE", "手续费", "QUERY", "查询"
);

item.setTransTypeName(
    TRANS_TYPE_NAMES.getOrDefault(r.getTransTypeCode(), r.getTransTypeCode())
    //                  ↑ 查不到就原样返回英文，不会崩
);
```

**为什么放代码常量而不是查 `trans_type` 字典表：**

| | 代码常量 | 字典表 |
|---|---|---|
| 性能 | 快（无额外查询） | 每次多一次关联查询 |
| 灵活性 | 改要重新部署 | 改数据即可 |
| 本项目选择 | ✅（交易类型固定 6 种） | — |

**③ Entity → DTO 的转换（Stream 写法）**

```java
return records.stream().map(r -> {
    TransDetailItem item = new TransDetailItem();
    item.setTransNo(r.getTransNo());
    ... 只搬 9 个字段 ...
    return item;
}).collect(Collectors.toList());
```

**等价于 for 循环**：`stream()` = for、`map` = 循环体、`collect` = add + return。

**为什么必须转**：`TransRecord` 有 19 个字段（含 `accountId`/`sessionId`/`deviceNo`），不能返回给前端。

## 3.9 退卡

### 问题

退卡后，原来的 `sessionToken` 还能用吗？

### 设计思路：**改状态，不删记录**

```java
public void ejectCard(String sessionToken) {
    AtmSession session = getValidSession(sessionToken);
    atmSessionMapper.updateStatus(session.getId(), 2);   // ← 只改 status，不 delete
}
```

```sql
update atm_session
set status = 2,
    logout_time = case when #{status} = 2 then now() else logout_time end
where id = #{id}
```

### 效果

```
token 字符串 → 还在数据库里（能查到）
会话         → 已失效（status=2 ≠ 1）
结果         → 再用这个 token 请求，getValidSession 抛 401「会话已结束」
```

### 为什么不删记录

```
① 留审计痕迹：谁在什么时间插卡、退卡、用的哪台机器
② 删了就无法回答"这张卡今天在 ATM001 上操作过几次"
③ atm_session 本质是"会话日志"，不是"临时缓存"
```

**这就是"可主动失效"的实现方式 —— 不删令牌，改状态。JWT 做不到这一点。**

## 3.10 管理端登录

### 问题

登录失败的提示怎么写？JWT 里放什么？

### 设计要点一：统一失败提示（防用户枚举）

```java
// 用户不存在
if (user == null) {
    throw new BusinessException(ResultCode.PASSWORD_ERROR, "用户名或密码错误");
}
// 密码错误
if (!passwordEncoder.matches(request.getPassword(), user.getPassword())) {
    throw new BusinessException(ResultCode.PASSWORD_ERROR, "用户名或密码错误");
}
```

**两种失败返回完全一样的提示。**

**如果分开提示：**

```
admin + 错密码 → "密码错误"        ← 泄露：admin 这个用户存在
asdfg + 任意   → "用户不存在"      ← 泄露：asdfg 不存在
    ↓
攻击者用常见用户名列表跑一遍
    → 得到系统里有哪些账号的完整名单
    → 只针对真实账号爆破（效率提升几百倍）
```

**这叫「用户枚举攻击」（User Enumeration）。**

### 设计要点二：JWT 里只放非敏感信息

```java
Jwts.builder()
    .subject(String.valueOf(userId))    // sub
    .claim("username", username)
    .claim("role", role)
    .issuedAt(now)
    .expiration(expiration)
    .signWith(key)
    .compact();
```

**为什么不多放：**

```
JWT 的 payload 是 Base64 编码，不是加密
任何人拿到 token 都能解开看到明文
    ↓
密码、手机号、身份证、余额 一律不能放
```

**三条结论：**

```
① JWT 里只放 userId / username / role 这类非敏感标识
② 签名只保证"没被篡改"，不保证"内容保密"
③ 要保密 → 用 HTTPS 传输
```

# 四、横切设计

## 4.1 统一响应

**所有接口（成功或失败）都返回同一个外壳：**

```json
{ "code": 200, "message": "操作成功", "data": {}, "timestamp": 1792893055095 }
```

**好处：**

```
① 前端只需判断 code == 200
② 业务错误不用靠 HTTP 状态码表达（HTTP 恒 200）
③ message 可以直接显示给用户（后端已写好中文）
```

## 4.2 全局异常处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)                 // 业务异常
    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 校验失败
    @ExceptionHandler(BindException.class)                     // 参数绑定失败
    @ExceptionHandler(MissingServletRequestParameterException.class)  // 缺参数
    @ExceptionHandler(HttpMessageNotReadableException.class)   // JSON 解析失败
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)      // 类型不匹配
    @ExceptionHandler(Exception.class)                         // 兜底
}
```

**Controller 里零 try-catch 的原因：** 异常自动被这里接住。

**⚠️ 两个例外（拦截器必须自己处理）：**

```
① 拦截器里 reject()：执行时还没进 Spring 处理链，advice 接不到 → 手动写 JSON
② Controller 自己 catch：异常被吞了，没抛出去 → advice 也接不到
```

**原理一句话：`@RestControllerAdvice` 只处理"从 Controller 方法往外抛"的异常。**

## 4.3 事务边界

| 方法 | 加事务 | 理由 |
|---|---|---|
| `withdraw` / `deposit` / `transfer` | ✅ | 动 2~3 张表，必须一起成功 |
| `verifyPassword` | ❌ **绝不能** | 抛业务异常会把错误计数回滚，导致永远锁不了卡 |
| `insertCard` | ⭕ 可加可不加 | 单条 insert 天然原子 |
| `queryBalance` / `queryTransactions` | ❌ | 只读，无回滚需求 |

**判断标准一句话：需要"一起回滚"才加。**

## 4.4 并发控制：4 类问题，4 种手段

| # | 并发问题 | 手段 | 代码位置 |
|---|---|---|---|
| 1 | **超扣 / 超卖** | SQL 条件更新（`where available_balance >= amount`） | `AccountMapper.decreaseBalance` |
| 2 | **丢失更新** | 原子自增（`set x = x + 1`） | `BankCardMapper.increasePwdErrorCount` |
| 3 | **死锁** | 按 `account_id` 升序更新 | `AtmServiceImpl.transfer` |
| 4 | **重复提交（幂等）** | 唯一索引 `uk_trans_no` | `trans_record` 表约束 |

**为什么不用 Redis / 分布式锁：**

```
synchronized       → 只在单 JVM 内有效，多实例部署立刻失效
Redis 分布式锁     → 多一个中间件、多一层网络、多一个故障点
SQL 条件更新       → 零额外依赖，一条语句解决
```

**共同的思想：把"判断"和"执行"交给同一个原子动作，而不是让应用层分两步做。**

## 4.5 幂等

**两层保障：**

```
① 数据库层：trans_record.trans_no 唯一索引 → 重复提交第二次 insert 被拒
② 业务层：转账的 3 条流水用 F/I 后缀，保证同一笔交易的记录互不冲突
```

**没有做"主动幂等"**（提交前先查 `selectByTransNo` 判断是否已处理）—— 靠唯一索引被动兜底，本期足够。

# 五、数据库设计要点

| 要点 | 说明 |
|---|---|
| 13 张表 | 权限 3 + 客户账户 3 + 交易 2 + 机具 2 + 审计 3 |

```
① 外键导致插入顺序严格受限，开发不便
② 分库分表时外键不可用
③ 一致性由 Service 层事务保证，不需要 DB 再管一遍
```

# 六、设计取舍与已知局限

## 6.1 主动做的取舍

| 取舍 | 选择 | 放弃的 | 理由 |
|---|---|---|---|
| 并发控制 | 数据库条件更新 | Redis 分布式锁 | 单机部署，不需要 |
| 会话管理 | 数据库会话 | 全用 JWT | JWT 无法主动失效 |
| 认证框架 | 只引 `spring-security-crypto` | Spring Security 全家桶 | 全家桶会拦所有接口，本项目要自己控白名单 |
| 接口文档 | 手写 Markdown | Swagger / Knife4j | 手写能写"为什么"，注解只能写"是什么" |
| 前端架构 | 单页状态机 | 多页面路由 | 6 个线性页面，状态机更贴合业务 |
| 交易类型 | 代码常量 Map | 字典表 | 类型固定 6 种，不值得多一次查询 |

## 6.2 已知局限（主动承认）

| # | 局限 | 影响 | 生产环境应有的做法 |
|---|---|---|---|
| 1 | **流水的 `before/after` 余额在并发下可能不准** | 极端并发时流水金额与实际有偏差 | 扣款后重新查余额，或 `SELECT ... FOR UPDATE` 加锁读 |
| 2 | **失败交易不落流水** | 交易失败只在应用日志留痕 | 用 `REQUIRES_NEW` 让流水独立事务提交 |
| 3 | **接口不存在返回 500 而非 404** | 路径打错时语义不对 | 加 `NoResourceFoundException` 处理器 |
| 4 | **`jwt.secret` 硬编码在配置文件** | 仓库公开 = 能伪造管理端 token | 改环境变量注入 `${JWT_SECRET}` |
| 5 | **未做日累计限额** | 只限制了单笔 | 加"当日累计/次数"查询 |
| 6 | **无单元测试** | 靠手工验证 | 补 Service 层关键方法测试 |
| 7 | **无主动幂等检查** | 靠唯一索引被动兜底 | 提交前先查 `selectByTransNo` |

## 6.3 如果重做一次，会改什么

```
① 金额校验抽成独立的 Validator，不要散在 AtmServiceImpl 里
   → 现在 validateAmount / validateDepositAmount 各写一遍，规则重复

② 流水的余额改成"扣款后重新查询"
   → 现在是读快照，并发下不准

③ 会话表拆成两张：atm_session（当前会话） + atm_session_log（历史）
   → 现在混在一起，退卡后的会话记录会一直留着

④ 接口文档用 springdoc 自动生成 + 手写补充说明
   → 手写 855 行太费时间，且改代码后容易忘同步

⑤ 补 Service 层单元测试
   → 现在全靠手工发请求验证，改代码后无法快速回归
```
