# ATM 自助管理系统 —— 接口文档

> 版本：v1.0　　生成日期：2026-10-24
> 服务地址：`http://localhost:8080`
> 适用范围：ATM 机具端（Flutter）+ 管理端预留接口

---

## 一、通用约定

### 1.1 统一响应格式

**所有接口**（无论成功失败）都返回同一个结构，由 `common/Result.java` 定义：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { },
  "timestamp": 1792808798311
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | Integer | 业务状态码，**200 表示成功**，其它见错误码表 |
| `message` | String | 提示信息，**可直接显示给用户** |
| `data` | 任意 | 业务数据；失败时通常为 `null` |
| `timestamp` | Long | 服务器时间戳（毫秒），用于排查问题 |

### 1.2 HTTP 状态码

**本项目统一返回 HTTP 200**，业务结果看 `code` 字段。

> 例外：拦截器拒绝的请求会返回真正的 HTTP 401（见 1.4）。

### 1.3 内容类型

- 请求：`Content-Type: application/json; charset=utf-8`
- 响应：`Content-Type: application/json`，编码 UTF-8
- 金额字段：JSON 中为数字（如 `1000.00`），**Java 侧用 BigDecimal，绝不用 double**

### 1.4 两类认证机制

| 端 | 认证方式 | 存放位置 | 是否需要 | 能否主动失效 |
|---|---|---|---|---|
| **管理端** | JWT | 请求头 `Authorization: Bearer <token>` | `/api/customer/**` 需要 | ❌ 只能等过期 |
| **ATM 机具端** | 会话 token | 请求体字段 `sessionToken` | 除插卡外都需要 | ✅ 改数据库状态立即失效 |

**拦截器白名单**（`config/WebMvcConfig.java`）：

```
/api/admin/login    管理员登录本身不需要 token
/api/atm/**         ATM 端用会话 token，不走 JWT
/api/hello          健康检查
/error              Spring 默认错误页
```

**结论：`/api/atm/**` 全部不需要 JWT，但业务层会自己校验 `sessionToken`。**

### 1.5 错误码全表

| code | 枚举名 | 默认提示 | 含义 / 触发场景 |
|---|---|---|---|
| 200 | SUCCESS | 操作成功 | 成功 |
| 400 | PARAM_ERROR | 参数校验失败 | `@Valid` 校验不通过、参数类型转换失败、缺少必填参数 |
| 401 | UNAUTHORIZED | 未登录或登录已过期 | JWT 无效；会话不存在 / 已结束 / 已超时 |
| 403 | FORBIDDEN | 没有权限访问 | 账号被禁用 |
| 404 | NOT_FOUND | 请求的资源不存在 | （预留） |
| 500 | FAIL | 操作失败 | 未预料的系统异常 |
| 1001 | CUSTOMER_NOT_FOUND | 客户不存在 | 按 id 查客户查不到 |
| 1002 | CARD_NOT_FOUND | 银行卡不存在 | 卡号不存在（含"对方卡号不存在"） |
| 1003 | ACCOUNT_NOT_FOUND | 账户不存在 | 卡对应的账户查不到，或账户状态异常 |
| 2001 | BALANCE_NOT_ENOUGH | 余额不足 | 取款 / 转账余额不够（转账会提示含手续费的总额） |
| 2002 | AMOUNT_LIMIT_EXCEED | 超出限额 | 单笔上限：取款 5000、存款 10000、转账 50000 |
| 2003 | AMOUNT_ILLEGAL | 金额不合法 | 金额 ≤ 0、或不是 100 的整数倍（取款/存款） |
| 2004 | PASSWORD_ERROR | 密码错误 | 登录密码错 / 交易密码错（提示会带剩余次数） |
| 2005 | CARD_LOCKED | 银行卡已被锁定 | 交易密码连续错 3 次后被锁定；插卡时检测到已锁定 |
| 2006 | CARD_STATUS_ABNORMAL | 银行卡状态异常 | 挂失 / 注销 / 过期 / 对方卡状态异常 |
| 2007 | CASH_NOT_ENOUGH | 本机现金不足 | 钞箱张数不够出钞 |
| 2008 | TRANSFER_TO_SELF | 不能给自己转账 | 转账目标卡号 == 本方卡号 |

## 三、ATM 端的完整使用流程

**Flutter 开发按这个顺序写：**

```
① POST /api/atm/insert-card        ← 输入卡号，拿到 sessionToken（存内存里）
        ↓
② POST /api/atm/verify-password    ← 输入 6 位交易密码
        ↓
   ┌────────────┬────────────┬────────────┬────────────┐
   │ 取款        │ 存款        │ 余额查询    │ 交易明细    │  ← 任意顺序、可重复
   │ withdraw   │ deposit    │ balance    │ transactions│
   └────────────┴────────────┴────────────┴────────────┘
   │ 转账 transfer                                     │
        ↓
③ POST /api/atm/eject-card         ← 退卡，会话失效
```

**关键约束**：

| 约束 | 值 | 说明 |
|---|---|---|
| 会话有效期 | **5 分钟无操作** | 每次成功调接口都会刷新 `last_active_time` |
| 交易密码错误上限 | **3 次** | 第 3 次直接锁卡（`card_status=2`） |
| 锁卡后 | 必须到柜台解锁 | 插卡时会提示"卡片已锁定（时间）" |
| 退卡后 | `sessionToken` 立即失效 | 再用会返回 401「会话已结束」 |
| **必须先验密码** | `verified = 1` | 未验密码只能调 `verify-password` / `eject-card`，其它接口返回 401「请先验证交易密码」 |

### 4.2 管理员登录

```
POST /api/admin/login
```

**请求字段**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `username` | String | ✅ | 管理员账号（seed 数据：`admin` / `operator` / `auditor`） |
| `password` | String | ✅ | 明文密码（seed 数据统一为 `admin123`） |

**请求示例**
```json
{ "username": "admin", "password": "admin123" }
```

**成功响应**
```json
{
  "code": 200,
  "message": "登录成功",
  "data": {
    "token": "eyJhbGciOiJIUzM4NCJ9.eyJzdWIiOiIxIiwidXNlcm5hbWUiOiJhZG1pbiIsInJvbGUiOiJhZG1pbiIsImlhdCI6MTc5MjgwODc5OCwiZXhwIjoxNzkyODE1OTk4fQ.xxx",
    "expiresIn": 7200,
    "username": "admin",
    "realName": "张伟",
    "role": "admin"
  },
  "timestamp": 1792808798311
}
```

| 响应字段 | 说明 |
|---|---|
| `token` | JWT，后续请求放 `Authorization: Bearer <token>` |
| `expiresIn` | 有效期（**秒**），当前 7200 = 2 小时 |
| `realName` | 显示用（"欢迎，张伟"） |
| `role` | 前端可据此决定显示哪些菜单 |

**失败场景**

| 情况 | code | message |
|---|---|---|
| 用户名或密码错 | 2004 | 用户名或密码错误 |
| 账号被禁用（status≠1） | 403 | 该账号已被禁用 |
| 用户名为空 | 400 | 用户名不能为空 |

**业务说明**

1. 按 `username` 查 `sys_user` 表
2. 用 `BCryptPasswordEncoder.matches(明文, 数据库哈希)` 校验密码
3. 校验通过后签发 JWT（Payload：`sub`=用户id、`username`、`role`，有效期 2 小时）
4. 更新 `last_login_time`
5. **安全设计**："用户不存在"和"密码错误"返回**同一句提示**，防止攻击者探测哪些账号存在（用户枚举攻击）

### 4.7 插卡（建立会话）⭐ 流程起点

```
POST /api/atm/insert-card
```

**请求字段**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cardNo` | String | ✅ | 银行卡号（19 位） |
| `deviceNo` | String | ❌ | 机具编号，不传默认 `ATM001` |

**请求示例**
```json
{ "cardNo": "6222020000000001", "deviceNo": "ATM001" }
```

**成功响应**
```json
{
  "code": 200,
  "message": "插卡成功",
  "data": {
    "sessionToken": "d9d80bd4522e43c48ea7a72da347d4d8",
    "cardNo": "6222********0001",
    "customerName": "张三",
    "message": "插卡成功，请输入 6 位交易密码"
  },
  "timestamp": 1792808798020
}
```

| 响应字段 | 说明 |
|---|---|
| `sessionToken` | **32 位随机串**，后续所有 ATM 操作都要带它。**只存在前端内存里，不要落盘** |
| `cardNo` | 已脱敏（前 4 + 星号 + 后 4），可直接显示 |
| `customerName` | 显示"欢迎，张三" |

**失败场景**（按代码执行顺序）

| 顺序 | 情况 | code | message 示例 |
|---|---|---|---|
| 1 | 卡号不存在 | 1002 | 银行卡不存在 |
| 2 | 已锁定 | 2005 | 卡片已锁定（2026-10-18T17:05:08），请联系银行解锁 |
| 3 | 已挂失 | 2006 | 卡片已挂失 |
| 4 | 已注销 | 2006 | 卡片已注销 |
| 5 | 过期 | 2006 | 卡片已过有效期，请更换新卡 |
| 6 | 卡号为空 | 400 | 卡号不能为空 |

**业务说明**

1. 按 `cardNo` 查 `bank_card`
2. 校验卡状态（1正常 / 2锁定 / 3挂失 / 4注销）
3. 校验有效期（`expire_date`，为 null 表示长期有效）
4. 查 `customer` 取姓名
5. **生成会话**：`session_no` + `token` 都是 UUID 去掉横线（32 位），插入 `atm_session`，`status=1`
6. 返回脱敏卡号

> **注意**：插卡只是"建立会话"，**还没有验证密码**。此时只能调 `verify-password`，不能直接取款（见第五章「已知问题」）。

### 4.8 验证交易密码

```
POST /api/atm/verify-password
```

**请求字段**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sessionToken` | String | ✅ | 插卡拿到的会话令牌 |
| `password` | String | ✅ | 6 位交易密码（seed 数据统一 `123456`） |

**成功响应**
```json
{ "code": 200, "message": "密码验证通过", "data": null, "timestamp": 1792808798220 }
```

**失败场景**

| 情况 | code | message |
|---|---|---|
| 密码错误，还剩 2 次 | 2004 | 密码错误，还可尝试 2 次 |
| 密码错误，还剩 1 次 | 2004 | 密码错误，还可尝试 1 次 |
| **第 3 次错误 → 锁卡** | **2005** | 密码连续错误 3 次，卡片已锁定，请联系银行 |
| 会话不存在 | 401 | 会话不存在，请重新插卡 |
| 会话已结束（已退卡） | 401 | 会话已结束，请重新插卡 |
| 会话超时 | 401 | 会话已超时（5 分钟无操作），请重新插卡 |
| 密码为空 | 400 | 密码不能为空 |

**业务说明（这是本项目最关键的逻辑之一）**

```
① 校验会话（存在 / status=1 / 未超时）
② 查卡、校验卡状态
③ BCrypt 校验密码
   ├─ 失败 → pwd_error_count 原子 +1（SQL: set x = x + 1）
   │         重新读最新值
   │         ├─ >= 3 → 锁卡（card_status=2, lock_time=now）→ 抛 2005
   │         └─ < 3  → 抛 2004，提示剩余次数
   └─ 成功 → pwd_error_count 归零
④ 刷新会话 last_active_time
```

**⚠️ 这个方法故意不加 `@Transactional`**

因为它会**抛业务异常**。如果加了事务，抛异常会把"错误次数 +1"和"锁卡"一起回滚 —— 用户就能无限次试密码。

**同理，`updateStatus(超时)` 也会被回滚，所以查询会话超时的逻辑也不能放在事务里。**

### 4.10 取款 ⭐ 核心交易

```
POST /api/atm/withdraw
```

**请求字段**

| 字段 | 类型 | 必填 | 限制 | 说明 |
|---|---|---|---|---|
| `sessionToken` | String | ✅ | — | 会话令牌 |
| `amount` | BigDecimal | ✅ | **100 ≤ amount ≤ 5000**，且必须是 **100 的整数倍** | 取款金额 |

**请求示例**
```json
{ "sessionToken": "d9d80bd4522e43c48ea7a72da347d4d8", "amount": 500 }
```

**成功响应**
```json
{
  "code": 200,
  "message": "取款成功",
  "data": {
    "transNo": "20261024102638637966",
    "amount": 500,
    "balanceAfter": 9500.00,
    "cashDetail": "100 元 × 5 张",
    "message": "请取走现金"
  },
  "timestamp": 1792808798311
}
```

| 响应字段 | 前端怎么用 |
|---|---|
| `transNo` | 交易流水号，可打印在凭条上 |
| `balanceAfter` | **ATM 屏幕上最显眼的数字**："您的余额为 9500.00 元" |
| `cashDetail` | 出钞时提示"请取走 100 元 × 5 张" |

**失败场景**

| 情况 | code | message |
|---|---|---|
| 金额 150（非 100 倍数） | 2003 | 取款金额必须是 100 的整数倍 |
| 金额 < 100 | 400 | 取款金额最少 100 元 |
| 金额 > 5000 | 400 | 单笔取款最多 5000 元 |
| 余额不足 | 2001 | 余额不足 |
| 钞箱张数不够 | 2007 | ATM 现金不足，请换台机器或改取其他金额 |
| 账户状态异常 | 1003 | 账户状态异常，无法取款 |

**业务说明（6 步，全部在一个事务里）**

```
① 校验会话 → 查卡 → 校验卡状态
② 金额校验：100 的整数倍、100~5000
③ 查账户（account 表，按 card_id 查活期 CNY 账户）
④ 扣款：update account set available_balance = available_balance - #{amount}
                        where id = #{id} and available_balance >= #{amount}
   → 返回 0 行 = 余额不足（数据库保证不会扣成负数）
⑤ 配钞：查钞箱（面额 100），张数够不够 → 扣张数
   → 不够就抛 2007，事务回滚，第 ④ 步扣的钱会撤销
⑥ 记流水（trans_type_code = WITHDRAW）
```

**⭐ 为什么要 `@Transactional`**

扣余额、扣钞箱、记流水动了 **3 张表**。如果第 ⑤ 步失败，第 ④ 步扣的钱必须撤回 —— 否则用户钱少了却没拿到现金。

**⭐ 为什么"余额校验"要写在 SQL 的 WHERE 里**

```sql
where available_balance >= #{amount}
```

如果先在 Java 里查余额判断再扣，两个并发请求会都读到旧值、都判断"够"，造成超扣。放进 WHERE 让数据库用行锁保证原子性。

### 4.14 转账 ⭐ 最复杂的业务

```

```

**请求字段**

| 字段 | 类型 | 必填 | 限制 |
|---|---|---|---|
| `sessionToken` | String | ✅ | — |
| `targetCardNo` | String | ✅ | 对方卡号，不能等于本方卡号 |
| `amount` | BigDecimal | ✅ | **1 ≤ amount ≤ 50000**，**不要求 100 整数倍** |

**请求示例**
```json
{
  "sessionToken": "d9d80bd4522e43c48ea7a72da347d4d8",
  "targetCardNo": "6222020000000002",
  "amount": 1000
}
```

**成功响应**
```json
{
  "code": 200,
  "message": "转账成功",
  "data": {
    "transNo": "20261024102638637966",
    "targetCardNo": "6222********0002",
    "targetName": "李四",
    "amount": 1000,
    "fee": 5.00,
    "totalAmount": 1005.00,
    "balanceAfter": 8995.00,
    "message": "转账成功"
  },
  "timestamp": 1792808798311
}
```

**手续费规则（三档）**

| 转账金额 | 0.5% 计算结果 | 实际收取 | 说明 |
|---|---|---|---|
| 100 | 0.5 | **1.00** | 不足最低，按 1 元收 |
| 1000 | 5.00 | **5.00** | 正常 |
| 20000 | 100.00 | **50.00** | 超最高，按 50 元封顶 |

**计算方式**：`amount × 0.005` 保留 2 位小数（四舍五入），再夹在 [1, 50] 之间。

**失败场景**

| 情况 | code | message |
|---|---|---|
| 转给自己 | 2008 | 不能给自己转账 |
| 对方卡号不存在 | 1002 | 对方卡号不存在 |
| 对方卡状态异常 | 2006 | 对方卡片状态异常，无法接收转账 |
| 余额不够（含手续费） | 2001 | 余额不足：转账 50000 元 + 手续费 50.00 元 = 50050.00 元 |
| 金额 < 1 | 400 | 转账金额最少 1 元 |
| 金额 > 50000 | 400 | 单笔转账最多 50000 元 |

**业务说明（11 步，全部在一个事务里）**

```
① 校验会话
② 查本方卡 + 校验状态
③ 不能转给自己（卡号比对）
④ 查对方卡 + 校验状态
⑤ 查双方账户
⑥ 算手续费：calcFee(amount)
⑦ 友好判断余额（availableBalance >= amount + fee）
⑧ 【防死锁】按 account_id 从小到大更新两边
⑨ 记 3 条流水
⑩ 刷新会话
⑪ 组装响应
```

**⭐⭐ 三个关键设计**

**（1）为什么要按 account_id 排序更新**

```
A(账户1) → B(账户2)  和  B(账户2) → A(账户1)  同时发生

如果都"先扣自己再加对方"：
   事务1 锁住账户1，等账户2
   事务2 锁住账户2，等账户1
   → 死锁，数据库报 Deadlock found

按 id 从小到大：两个事务都先获取账户1，再获取账户2 → 排队执行，不会死锁
```

**（2）为什么记 3 条流水**

| 流水 | 归属 | 金额 | 用途 |
|---|---|---|---|
| `TRANSFER_OUT` | 转出方 | 转账金额 | 本方账单里能查到"转出 1000" |
| `FEE` | 转出方 | 手续费 | 手续费独立可查，便于对账 |
| `TRANSFER_IN` | **转入方** | 转账金额 | **让对方账户的明细里能看到这笔收入** |

**`trans_no` 后缀**：主流水用 `transNo`，手续费用 `transNo + "F"`，转入用 `transNo + "I"` —— 因为 `trans_record.trans_no` 上有**唯一索引** `uk_trans_no`，三条流水必须不同号。

**（3）余额链是自洽的（可用来验证）**

```
转账 1000、手续费 5：

TRANSFER_OUT   10000.00 → 8995.00     扣 1005（本金 + 手续费）
FEE             9000.00 → 8995.00     扣 5    ← 9000 = 10000 - 1000
TRANSFER_IN     5000.00 → 6000.00     加 1000
```

**三条流水串起来能完整还原这笔交易。这就是财务对账依赖的东西。**

## 六、Flutter 开发须知（重要）

### 6.1 请求封装建议

```dart
// 统一封装，避免每个页面重复写
Future<Map<String, dynamic>> post(String path, Map<String, dynamic> body) async {
  final res = await http.post(
    Uri.parse('$baseUrl$path'),
    headers: {'Content-Type': 'application/json; charset=utf-8'},
    body: jsonEncode(body),
  );
  return jsonDecode(utf8.decode(res.bodyBytes));   // ⚠️ 用 bodyBytes + utf8 解码，否则中文乱码
}
```

> ⚠️ **中文乱码坑**：不要用 `res.body`，要用 `utf8.decode(res.bodyBytes)`。

### 6.2 判断成功与失败的统一写法

```dart
final json = await post('/api/atm/withdraw', {
  'sessionToken': sessionToken,
  'amount': amount,
});

if (json['code'] == 200) {
  // 成功：取 json['data']
  setState(() => balance = json['data']['balanceAfter']);
} else {
  // 失败：直接显示 json['message']（后端已经写好了给人看的中文）
  showDialog(... json['message'] ...);
}
```

**因为所有错误都用 `code != 200` + 可读的 `message` 表达，前端不需要写复杂的错误分支。**

### 6.3 金额处理

```dart
// 后端返回的是 JSON 数字，Dart 里可能解析成 int 或 double
// 统一转成 double 再格式化，避免 500 显示成 500.0 这种
double amount = (json['data']['amount'] as num).toDouble();
String display = amount.toStringAsFixed(2);   // "500.00"
```

### 6.4 状态机（单页方案）

```dart
int step = 0;                  // 0=插卡 1=密码 2=菜单 3=取款 4=存款 5=结果
String sessionToken = '';
String maskedCardNo = '';
String customerName = '';

// 插卡成功后
setState(() {
  sessionToken = json['data']['sessionToken'];
  maskedCardNo = json['data']['cardNo'];
  customerName = json['data']['customerName'];
  step = 1;
});

// 退卡时
sessionToken = '';             // 清空，防止误用
step = 0;
```

### 6.5 会话超时

后端 **5 分钟无操作**会超时。前端可以：

- **简单做法**：不主动处理，超时后调接口会返回 401，显示"会话已超时，请重新插卡"并跳回插卡页
- **进阶做法**：前端也计时，4 分钟时在界面上显示倒计时提示
